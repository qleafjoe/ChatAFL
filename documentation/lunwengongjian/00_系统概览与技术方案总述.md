# ChatAFL 扩展版：验证驱动的 LLM 协议模糊测试 — 系统概览与技术方案总述

> **一句话定义**：在 ChatAFL（NDSS 2024）的 LLM 辅助协议模糊测试框架上，增加验证层（Format/Grammar/Context）、反馈重试机制和 Soft Validation 软准入策略，对 LLM 输出进行质量治理，提升模糊测试的输入合法性和状态探索效率。

## 1. 问题动机

传统协议模糊测试（AFLNet 等）存在三个核心瓶颈：

| 瓶颈 | 表现 | ChatAFL 的 LLM 解决方案 |
|------|------|------------------------|
| **语法盲区** | 不了解协议语法，盲目变异破坏消息结构 | Grammar Setup：LLM 提取协议模板 → PCRE2 正则 → 结构感知变异 |
| **种子覆盖不足** | 初始种子缺少关键消息类型，难以到达深层状态 | Seed Enrichment：LLM 识别缺失类型 → 自动插入合适位置 |
| **覆盖停滞** | 连续变异无法突破状态瓶颈 | Stall Breaking：LLM 根据通信历史生成突破性消息 |

**但 LLM 输出存在质量问题**：格式错误、语法违规、状态上下文不满足，可能导致目标服务器拒绝、模糊器 hang、或浪费执行预算。本扩展的核心贡献是引入**验证驱动的 LLM 输出治理**。

## 3. 三个核心 LLM 策略

### 3.1 Grammar Setup（语法模板提取）

**目标**：让 LLM 学习协议消息模板，编译为 PCRE2 正则，引导结构感知变异。

**流程**：
1. Few-shot Prompt（提供 RTSP DESCRIBE + HTTP GET 示例）
2. 多轮补充（"other templates" 追问遗漏命令）
3. 5 次自洽采样 → 一致性过滤（字段出现 >= 3 次才保留）
4. 编译为 PCRE2 正则模式（头部模式 + 字段模式）

**关键代码**：`setup_llm_grammars()` → `construct_prompt_for_templates()` → `extract_message_grammars()` → `extract_message_pattern()`

### 3.2 Seed Enrichment（种子丰富）

**目标**：识别现有种子中缺失的消息类型，让 LLM 自动插入。

**流程**：
1. 解析种子 → 提取已有消息类型 → 与 `message_types_set` 对比 → 找出缺失类型
2. 生成 C(n,1) + C(n,2) 的类型组合（最多 10 个缺失类型，每次最多插入 2 种）
3. LLM 生成包含缺失类型的完整请求序列
4. 后处理 + 去重 + 验证 + 反馈重试 → 写入 `enriched_*` 文件

**关键代码**：`enrich_testcases()` → `enrich_sequence_with_prompt()` → `validate_llm_sequence_with_mode()`

### 3.3 Stall Breaking（停滞突破）

**目标**：当连续 512 次变异无新覆盖时，LLM 根据通信历史生成突破性消息。

**流程**：
1. 触发条件：`uninteresting_times >= 512 && chat_times < 512`
2. 构建通信历史（请求-响应对，截断到 4000 字符）
3. LLM 生成下一条客户端请求（温度 1.5，高多样性）
4. 提取 + 格式化 + 验证 + 反馈重试 → 执行

**关键代码**：`fuzz_one()` 中的停滞检测 → `construct_prompt_stall()` → `extract_stalled_message()` → `validate_llm_message_with_mode()`

## 4. 验证层概述

### 4.1 三级验证模式

| 模式 | 环境变量 | 行为 |
|------|---------|------|
| `LLM_VALIDATE_DISABLED` | `AFL_LLM_VALIDATION=0` | 跳过所有校验 |
| `LLM_VALIDATE_FORMAT_ONLY` | `AFL_LLM_VALIDATION=1, STRICT=0` | 仅检查结构格式（CRLF、可打印字符、请求行格式） |
| `LLM_VALIDATE_FULL` | `AFL_LLM_VALIDATION=1, STRICT=1` | 格式 + 语法（有效方法/命令）+ 上下文（状态机） |

### 4.2 四种验证结果

| 结果 | 含义 | 处理 |
|------|------|------|
| `LLM_VALID_OK` | 通过 | 接受 |
| `LLM_VALID_FORMAT_FAIL` | 缺少 CRLF、非打印字符、请求行格式错误 | 反馈重试 → Soft Validation |
| `LLM_VALID_GRAMMAR_FAIL` | 无效方法/命令、缺少必需头字段 | 反馈重试 → Soft Validation |
| `LLM_VALID_CONTEXT_FAIL` | 协议状态机违规（如 PLAY 缺少 Session） | 反馈重试 → Soft Validation |
| `LLM_VALID_NO_GAIN` | 有效但无新覆盖率（仅用于执行后归因） | 记录日志 |

### 4.3 反馈重试机制

三层重试架构：
```
第3层: 调用方重试（GRAMMAR_RETRIES=5, STALL_RETRIES=2, ENRICHMENT_RETRIES=5）
  └─ 第2层: 反馈重试（LLM_FEEDBACK_MAX_RETRIES=3）
       └─ 第1层: HTTP 级重试（curl 失败/JSON 解析失败时重试）
```

反馈 Prompt 核心设计：将失败消息 + 错误详情注入 prompt，让 LLM 生成修复后的消息。

### 4.4 Soft Validation 软准入

在反馈重试仍失败后，按失败类型概率性接纳：

| 失败类型 | 接纳概率 | 原因 |
|----------|---------|------|
| `FORMAT_FAIL` | 0% | 格式错误通常被服务器直接拒绝 |
| `GRAMMAR_FAIL` | 5% | 非法方法可能触发错误处理路径 |
| `CONTEXT_FAIL` | 30% | 语法合法但上下文不满足，最可能探索状态机错误处理 |

被 Soft 接纳的种子降低优先级（`llm_priority = 2`），避免噪声挤占正常种子。

TR 系列是最新消融实验，行为硬编码在源码中（`#define`），env.sh 仅含注释。

| 变体 | 层次 | 关键特性 | afl-fuzz.c md5 | chat-llm.c 行数 |
|------|------|---------|----------------|-----------------|
| **TR1** | 纯 LLM | 无 PromptClean、无验证、无反馈 | `608d0b5c` | 1348 (Group A) |
| **TR2** | + PromptClean | 鲁棒性检查（null/type 检查） | `c031c645` | 1348 (Group A) |
| **TR3** | + Hard Validation | 完整验证 + 反馈重试（硬编码） | `0f847d17` | 1647 (Group B) |

```
TR1 (纯LLM) → TR2 (+PromptClean) → TR3 (+Hard Validation+Feedback) → TR4 (+Soft Validation)
```

## 6. 与相关工作的定位

| 相关工作 | 核心方法 | ChatAFL 扩展的差异 |
|----------|---------|-------------------|
| **MultiFuzz** | RAG + RFC 文档注入 + 多智能体 | ChatAFL 不依赖 RFC，使用 Few-shot + 自洽采样 |
| **GLMFuzz** | 漏洞知识图谱引导 | ChatAFL 不针对漏洞模式，专注协议语法和状态覆盖 |
| **StruFuzz** | 种子结构感知变异 | ChatAFL 的 epsilon-greedy 已实现结构感知（50% 利用语法） |
| **StatePre** | 状态处理优化 | ChatAFL 的状态选择算法（RANDOM/ROUND_ROBIN/FAVOR）已有类似机制 |
| **DerandomPre** | 稳定性预处理 | ChatAFL 的 `clean_llm_response()` 提供部分去随机化 |
| **LLMgSSA** | LLM 引导状态选择 | ChatAFL 的停滞突破是状态选择的补充 |
| **PSG** | 多样化种子生成 | ChatAFL 的 Seed Enrichment 是种子多样化的特化 |
| **RTSGen** | RFC + 流量引导 | ChatAFL 不依赖流量捕获 |
| **MALF** | 多智能体工业协议 | ChatAFL 是单 LLM 多调用点架构 |

**ChatAFL 扩展的独特贡献**：验证驱动的 LLM 输出治理（三层验证 + 反馈重试 + Soft Validation），而非 LLM 调用架构本身的改变。
