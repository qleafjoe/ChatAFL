## 1. 消融目标

逐层分离三个工程改进的独立贡献：

```
TR1 (纯LLM) → TR2 (+PromptClean) → TR3 (+Hard Validation+Feedback) → TR4 (+Soft Validation)
```

可回答的问题：
1. Prompt/IO 清洗（PromptClean）相对纯 LLM 是否已有收益？
2. 严格验证是否提升输入质量，还是牺牲探索性？
3. Soft Validation 是否能找回 Hard Validation 丢弃的边界输入价值？

## 2. TR1-TR4 变体定义

### 2.1 总览

| 变体 | 层次 | 关键特性 | 控制方式 |
|------|------|---------|---------|
| **TR1** | 纯 LLM | 无 PromptClean、无验证、无反馈 | 硬编码（`#define` 缺失） |
| **TR2** | + PromptClean | 鲁棒性检查（null/type 检查） | 硬编码 |
| **TR3** | + Hard Validation | 完整验证 + 反馈重试 | 硬编码 `#define` |
| **TR4** | + Soft Validation | 概率接纳 + 降低种子优先级 | 硬编码 `#define` |

### 2.2 TR1：纯 LLM（真实 ChatAFL-base）

**目的**：建立真正的原始 ChatAFL 对照。

**代码来源**：`ChatAFL-TR1/`

**关键特性**：
- 无 `clean_llm_response()` 鲁棒性检查
- 无 `llm-validator.c/h` 验证框架
- 无反馈重试机制
- LLM 输出直接使用（仅依赖 `extract_stalled_message()` 和 `format_request_message()` 的基本后处理）

**env.sh**：注释-only（"intentionally does not set AFL_LLM_* ablation flags"）

### 2.3 TR2：+ PromptClean

**目的**：隔离 prompt/IO 清洗工程改动的收益。

**代码来源**：`ChatAFL-TR2/`

**关键特性**：
- `clean_llm_response()` 输出清洗（拒绝检测 + JSON 提取 + Markdown 剥离 + CRLF 转换）
- Grammar 解析中的鲁棒性检查（null/type 检查 JSON 对象）
- prompt 输出约束增强（"Output ONLY strictly valid JSON. NO markdown, NO code blocks, NO explanations."）
- 无验证框架、无反馈重试

**与 TR1 的差异**：`afl-fuzz.c` md5 不同（`c031c645` vs `608d0b5c`），增加了 PromptClean 鲁棒性检查

**env.sh**：注释-only（"TR2 has fixed PromptClean behavior in source code"）

### 2.4 TR3：+ Hard Validation + 反馈重试

**目的**：评估严格验证的代价与收益。

**代码来源**：`ChatAFL-TR3/`

**关键特性**：
- 包含 `llm-validator.c/h` 验证框架
- 完整验证（`TR_LLM_VALIDATION=1`, `TR_LLM_VALIDATION_STRICT=1`）
- 反馈重试（`TR_LLM_FEEDBACK=1`, `TR_LLM_FEEDBACK_MAX_RETRIES=3`）
- 无 Soft Validation、无 Post-gain

**env.sh**：注释-only（"TR3 has fixed Hard Validation + feedback behavior in source code"）

**注意**：所有标志通过 `#define` 硬编码在 `afl-fuzz.c` 中，不依赖环境变量。

### 2.5 TR4：+ Soft Validation

**目的**：验证被 Hard Validation 丢弃的候选中，是否存在对状态机探索有价值的边界输入。

**代码来源**：`ChatAFL-TR4/`

**关键特性**：
- 包含 TR3 的所有特性
- 增加 Soft Validation 软准入机制
- 硬编码的接纳概率：`FORMAT_FAIL=0%`, `GRAMMAR_FAIL=5%`, `CONTEXT_FAIL=30%`
- 软接纳种子优先级降低：`llm_priority=2`
- 文件名前缀标记：`soft_enriched_*`

**env.sh**：注释-only（"TR4 has fixed Hard Validation + feedback + Soft Validation behavior in source code"）

## 3. TR 变体源码差异分析

### 3.1 afl-fuzz.c 分组（按 md5）

| Hash | 变体 | 关键特性 |
|------|------|---------|
| `608d0b5c` | TR1 | 无 PromptClean、无验证、无 env var 读取 |
| `c031c645` | TR2, V0 | 有 PromptClean 鲁棒性检查 |
| `0f847d17` | TR3 | 硬编码 `#define`: validation=1, strict=1, feedback=1, max_retries=3 |
| `9c1ac187` | TR4 | 同 TR3 + soft validation: soft_accept rates (format=0%, grammar=5%, context=30%), seed_priority=2 |
| `960bd38a` | V1, V2 | Env-var 控制验证，所有标志默认为 0 |
| `44de9e69` | ChatAFL | Env-var 控制，增加 seed dedup、动态权重、`is_llm_seed`/`llm_priority` 字段 |

### 3.2 chat-llm.c 分组

| 组别 | 变体 | 行数 | 特性 |
|------|------|------|------|
| Group A | TR1, TR2, V0 | 1348 | 无验证基础设施（无 `llm-validator.h` include） |
| Group B | TR3, TR4, ChatAFL | 1647 | 有验证基础设施（含 `llm_feedback_retry_*` 函数） |

### 3.3 关键代码差异

**TR1 vs TR2**：
- TR2 的 `afl-fuzz.c` 在 Grammar 解析循环中增加了 null/type 检查
- TR2 的 `chat-llm.c` 与 TR1 相同（PromptClean 在两个组中都存在）

**TR2 vs TR3**：
- TR3 增加 `#include "llm-validator.h"` 和验证框架链接
- TR3 硬编码所有验证标志（`#define TR_LLM_VALIDATION 1` 等）
- TR3 增加 `get_llm_validation_mode()` 和 `current_validation_protocol_type()` 辅助函数

**TR3 vs TR4**：
- TR4 增加 `should_soft_accept_llm_result()` 函数
- TR4 增加 `llm_seed_priority` 字段到队列条目结构
- TR4 硬编码软接纳概率和种子优先级

## 4. 与 V 系列和基准的关系

### 4.1 V 系列（上一轮实验）

| 变体 | 等价 TR | 差异 |
|------|---------|------|
| V0 | TR2 | afl-fuzz.c 相同（md5: `c031c645`），V0 通过 env.sh 关闭所有标志 |
| V1 | — | 仅格式验证（STRICT=0），无 TR 对应 |
| V2 | TR3 | V2 通过 env.sh 控制，TR3 通过 `#define` 硬编码 |
| ChatAFL | — | 完整版（含 Post-gain、seed dedup、动态权重），无 TR 对应 |

**关键差异**：V 系列通过 `env.sh` 环境变量控制行为，TR 系列通过源码硬编码。TR 系列是最新实验。

### 4.2 基准 ChatAFL

**代码来源**：`baseline/ChatAFL/ChatAFL/`

**与 TR1 的关系**：TR1 最接近基准论文原始代码，但 TR1 的 `chat-llm.c` 已有 MiniMax 适配（`LLM_URL`/`LLM_TOKEN`/`LLM_MODEL` 环境变量、统一 chat endpoint），而基准版使用硬编码的 OpenAI `OPENAI_TOKEN` 宏。

**与 TR2 的关系**：TR2 的 PromptClean 改动（`clean_llm_response()`、更大的 Token 预算、`CHATTING_THRESHOLD=512`）是相对于基准的工程改进。

**详细差异**：见 `区别/基准ChatAFL与扩展版对比分析.md` 和 `区别/差异速查表.md`。

## 5. 消融矩阵与可证明结论

### 5.1 对比关系

| 对比 | 可证明结论 |
|------|-----------|
| TR1 vs aflnet | LLM 辅助（语法提取+种子丰富+停滞突破）的整体贡献 |
| TR2 vs TR1 | PromptClean（输出清洗+鲁棒性检查）的独立贡献 |
| TR3 vs TR2 | Hard Validation + 反馈重试的独立贡献 |
| TR4 vs TR3 | Soft Validation 软准入的独立贡献 |

### 5.2 不能直接证明的结论

- 不能单独证明"feedback retry 的独立贡献"，因为 TR3 硬编码了 validation + feedback
- 不能把 TR2 vs TR1 简化为"格式验证贡献"，TR2 同时包含 PromptClean
- `LLM_VALID_OK` 只表示执行前验证通过，不代表一定产生新覆盖或新状态
- `LLM_VALID_NO_GAIN` 属于执行后收益分类，不表示 LLM 输出非法

## 6. 实验运行指南

### 6.1 运行命令

```bash
# TR1 实验
./run_tr_ablation.sh tr1 full    # 720分钟, 10容器

# TR2 实验
./run_tr_ablation.sh tr2 full

# TR3 实验
./run_tr_ablation.sh tr3 full

# TR4 实验
./run_tr_ablation.sh tr4 full

# 短跑筛选
./run_tr_ablation.sh tr1 short   # 120分钟, 3容器

# Smoke test
./run_tr_ablation.sh tr1 smoke   # 10分钟, 1容器
```

### 6.2 三阶段执行

| 阶段 | 时长 | 容器数 | 目的 |
|------|------|--------|------|
| Smoke test | 10 min | 1 | 验证工程正确性 |
| Short screening | 120 min | 3 | 快速筛选参数 |
| Formal repeats | 720 min | 10 | 正式重复实验 |

### 6.3 重复次数

建议每个变体至少重复 3 次，每次使用不同的随机种子。10 容器 = 10 次重复（每个容器 1 个 CPU）。

## 7. 指标体系

### 7.1 主指标

| 指标 | 来源 | 用途 |
|------|------|------|
| line coverage | gcovr HTML/CSV | 代码覆盖率主结果 |
| branch coverage | gcovr HTML/CSV | 分支探索能力 |
| paths_total | `fuzzer_stats` | AFL 队列规模 |
| state count | `plot_data` / IPSM | 协议状态覆盖 |
| transition count | `ipsm.dot` edge count | 状态转移覆盖 |

### 7.2 验证层指标

| 指标 | 来源 | 用途 |
|------|------|------|
| validation pass rate | `llm-validation/*.csv` | LLM 输出合法性 |
| fail type distribution | `reason` 字段 | 格式/语法/上下文失败分布 |
| feedback recovery rate | feedback 前后记录 | 验证驱动修复价值 |
| no_gain ratio | post execution 记录 | LLM 候选无收益比例 |
| soft_accept gain rate | Soft 日志 | Soft Validation 是否真的有效 |

### 7.3 成本指标

| 指标 | 来源 | 用途 |
|------|------|------|
| execs_done | `fuzzer_stats` | 总执行量 |
| execs_per_sec | `fuzzer_stats` | 执行效率 |
| chat_times | `plot_data` | LLM 调用成本 |
| coverage per LLM call | coverage / chat_times | LLM 性价比 |
| new_state per LLM call | new states / chat_times | 状态探索性价比 |

## 8. 时间不一致问题分析

### 8.1 问题描述

所有变体应运行相同时间（如 800 分钟），但实验数据显示不同变体的实际运行时间不同（如 aflnet 13.34h, v0 8.52h, v1 8.37h, v2 10.50h）。

### 8.2 根因

`start_time` 是在 `setup_llm_grammars()` 和 `enrich_testcases()` **之后**设置的。LLM 启动时间（Grammar Setup 的 5×2 次 LLM 调用 + Seed Enrichment 的 N 次调用）被排除在 `fuzzer_stats` 的时间统计之外，但包含在 wall-clock timeout 中。

### 8.3 影响

- `fuzzer_stats` 中的 `run_time` 不等于实际 wall-clock 时间
- LLM 调用越多的变体，实际可用的 fuzzing 时间越短
- aflnet（无 LLM）的 fuzzing 时间最长

### 8.4 解决方案

1. 在论文中明确报告 wall-clock 时间而非 `fuzzer_stats` 时间
2. 或在代码中将 `start_time` 移到 `setup_llm_grammars()` 之前
3. 或使用 `AFL_LLM_SKIP_STARTUP=1` 跳过启动阶段 LLM 调用（需要预缓存语法）

## 9. 预期结论模板

### 9.1 如果 TR2 优于 TR1

说明 PromptClean 本身已有明显贡献。论文必须把验证层贡献建立在 `TR3/TR4 vs TR2`，而不是 `TR3/TR4 vs TR1`。

### 9.2 如果 TR3 低于 TR2

这不是失败，而是说明严格验证有探索性损失。重点转向：

> "Hard Validation reduces invalid/hanging executions but may discard boundary inputs."

这正好引出 TR4 (Soft Validation)。

### 9.3 如果 TR4 高于 TR3

这是最理想的主结论：

> "Soft Validation recovers part of the exploration value lost by strict validation while keeping validation-driven observability."

需要进一步证明收益主要来自 `CONTEXT_FAIL` soft admission，而不是随机噪声。

### 9.4 如果 TR4 与 TR3 持平

仍可成立的结论：

> "Validation-driven logging and feedback make LLM fuzzing measurable, but low-probability admission does not consistently improve coverage on these targets."

此时论文应弱化覆盖率提升，强调可解释性、风险边界和负结果。

### 9.5 如果 TR4 低于 TR3

说明噪声稀释成立。应收缩 Soft 参数（`FORMAT_FAIL=0, GRAMMAR_FAIL=0, CONTEXT_FAIL=10~20`），并把 TR4 作为消融负例。
