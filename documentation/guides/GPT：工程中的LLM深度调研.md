# 科研与工程中项目代码调用大语言模型的系统化调研提纲

## 研究问题定义与分类体系

本文建议把“项目代码调用 LLM”定义为：在科研或工程流水线中，程序以 API、工具调用、代理循环或混合编排的方式引入语言模型，使模型输出直接影响后续计算、决策、文档、代码、实验或人类判断；把“某次调用值得”定义为：相对一个明确 baseline，在同等约束下带来了可测量的净收益，而且该收益能够覆盖直接成本、二次验证成本、风险暴露和长期维护复杂度。这个定义之所以需要系统化，是因为 LLM 已经同时进入软件工程任务空间与科研工作流：SE 综述显示其已覆盖大量代码相关任务，科学研究综述则显示其已经渗透到假设发现、实验规划与实现、写作和同行评审等阶段；与此同时，现实系统开始通过工具调用、MCP 与 A2A 等协议把模型嵌入可执行工作流，而不再只是“问答接口”。 citeturn29view3turn22view1turn20view4turn26view1

从综述写作角度，最清晰的 taxonomy 不是按模型家族分，而是按**调用生命周期**分：是否调用、给什么上下文、要求什么输出契约、如何验证、如何证明值得。这个五层结构与工程上的“路由—上下文工程—输出契约—质量门控—价值评估”链条一致，也与科研中“方法—数据—结果—验证—效益/伦理”写作逻辑一致。对需要外部环境交互的任务，Google 的 agentic 评估给出一个很实用的边界定义：真正需要 agent 的任务通常同时具有持续多步交互、在部分可观测环境中迭代搜集信息、以及根据反馈自适应修正策略这三个特征；而 Anthropic 与 OpenAI 的工具文档则把“模型输出文本”与“模型发起可执行工具调用”清楚地区分开来。 citeturn32view4turn19view1turn18view1

### 科研场景与工程场景对比

下表综合科学研究综述、出版与评审政策、SE 综述以及 NIST 风险框架整理。科研场景的核心是**证据、责任与可复现**；工程场景的核心是**SLA、自动化与副作用控制**。 citeturn22view1turn29view1turn20view0turn28view0turn28view1turn28view2

| 维度 | 科研场景 | 工程实践场景 |
|---|---|---|
| 首要目标 | 发现、分析、写作、评审辅助、实验吞吐 | 自动化交付、效率提升、稳定运行、缺陷减少 |
| 真值来源 | 文献、实验结果、数据与方法学规范 | 规格、业务规则、代码库、日志、测试、线上行为 |
| 容错性 | 对事实错误、伪引文、误导性评审通常很低 | 取决于业务；客服草稿可容错，代码执行与资金操作不可容错 |
| 责任结构 | 作者/审稿人/编辑必须担责，AI 不能担责 | 产品 owner、开发团队、运维与安全团队担责 |
| 隐私与保密 | 手稿、审稿、未公开结果高度敏感 | 内部代码、日志、用户数据、凭据同样敏感 |
| 验证重点 | 事实正确、引文存在、方法透明、结果可复现 | 契约正确、可执行、测试通过、无越权副作用 |
| 人在回路 | 往往是强制性的，尤其是评审和发表环节 | 可按风险分层；高风险动作需人工批准 |
| 发布节奏 | 通常较慢，但对长期可信度要求高 | 通常较快，需要持续监控和回归 |
| 失败后果 | 伤害学术诚信、误导结论、泄漏评审机密 | 引入缺陷、越权操作、成本飙升、服务不稳定 |

### 任务类型矩阵

下表不是按模型能力分，而是按“项目代码为什么要调 LLM”分。任务目标、约束和失败模式综合自软件工程与科学研究综述、SWE-bench、AgentBench、RAG、ReAct/Toolformer 以及同行评审风险研究。 citeturn29view3turn22view1turn21view2turn21view3turn30view2turn31view4turn31view3turn27view0turn27view2

| 任务类型 | 典型目标 | 主要约束 | 常见失败模式 | 建议的 LLM 角色 |
|---|---|---|---|---|
| 代码生成 | 从自然语言规格到函数/模块/脚本 | 语法、类型、依赖、风格、测试 | 编译失败、边界条件遗漏、伪 API | 候选生成器，不应绕过测试 |
| 代码修复 | 根据 issue、报错、测试失败给 patch | 需理解跨文件依赖和运行环境 | 修复错位、修一处坏两处、补丁无法应用 | 生成补丁候选 + 自动测试 |
| 文档理解 | 摘要、问答、需求抽取、变更对比 | 文档长、来源多、时效性强 | 断章取义、过时信息、引用错误 | 检索增强总结器 |
| 实验设计 | 生成实验方案、变量控制、假设检查 | 学科知识、因果与统计规范 | 设计混淆、不可执行、伦理遗漏 | 提案助手，不替代方法学审查 |
| 数据分析 | 生成分析计划、SQL/Python、解释结果 | 数据口径、可重现、统计检验 | 错检验、伪相关、绘图误导 | 分析 copilot + 沙盒执行 |
| 代理执行 | 浏览、检索、调用 API、改文件 | 外部环境、权限、状态、回滚 | 提示注入、越权、错误传播 | 受限 agent，需要 guardrails |
| 工作流编排 | 路由到工具/模型/人工节点 | 成本、延迟、互操作、审计 | 路由错误、上下文丢失、循环调用 | 协调器或路由器 |
| 测试生成 | 生成单测、属性测试、回归样例 | 覆盖率、预言机质量 | 只测表面路径、伪阳性/伪阴性 | 测试候选生成器 |
| 审稿辅助 | 总结贡献、找风险点、对齐 rubric | 保密、偏见、责任、政策 | 被提示词操控、偏向接受、伪批评 | 人类审稿辅助，不宜自动决策 |
| 知识检索增强 | 把已有知识变成可问答与可追溯答案 | 检索质量、证据覆盖、可更新 | 检索漂移、证据缺失、幻觉放大 | RAG 生成器或证据整合器 |

## 什么时候应调用 LLM

### 关键定义

“什么时候该调用 LLM”的本质不是“模型是否足够强”，而是“问题是否主要受**语义理解、开放式生成、模糊意图解析或多步推理**约束，而不是受**确定规则、精确检索、数值计算或窄任务分类**约束”。Toolformer 明确指出，语言模型在开放任务上很强，但在算术和事实查找等基础功能上往往不如更小、更专用的工具或模型；RAG 则表明，一旦任务是知识密集型且要求可更新、可溯源的证据，单靠参数记忆通常不够；ReAct 进一步说明，当任务既要推理又要与外部环境交互时，“只生成文本”会受制于幻觉和错误传播，而“推理+行动”更合适。 citeturn31view3turn30view2turn31view4

OpenAI 的 reasoning 模型文档也给出一个工程上很实用的信号：推理型模型特别适合复杂问题求解、编码、科学推理和多步 agent 工作流，但它们会消耗额外 reasoning token，因此“该不该调用更强的 LLM”本身也应被视为一个预算分配问题，而不是默认选项。MCP 的 schema 甚至把速度、成本、智能作为并列优先级显式编码，说明现代编排系统已经把“模型选择”视作多目标优化，而非单一精度最大化。 citeturn25view4turn20view3

### 可直接用于论文的调用决策矩阵

| 判断维度 | 优先传统程序逻辑/规则系统 | 优先检索系统/专用模型 | 优先单轮 LLM 调用 | 优先多轮 agent 调用 |
|---|---|---|---|---|
| 任务复杂度 | 低，映射关系明确 | 中，答案存在于语料或标签空间 | 中高，需要语义变换或开放式生成 | 高，需要多步试探、外部反馈和状态更新 |
| 模糊性/欠规格 | 低 | 低到中 | 高 | 高且动态变化 |
| 规则可覆盖度 | 高 | 中 | 低 | 低 |
| 错误容忍度 | 极低 | 低 | 中到高，或可被后验验证 | 仅当有强验证和回滚时可接受 |
| 成本/延迟预算 | 极紧 | 较紧 | 中 | 宽松或高价值 |
| 外部工具或数据库 | 不需要 | 主要用于检索或分类 | 可选 | 常常必需 |
| 输出副作用 | 不应有副作用 | 通常无副作用 | 通常无副作用或弱副作用 | 可能有强副作用，必须治理 |
| 人类参与 | 可无 | 可无 | 建议用于高风险审核 | 高风险动作通常应强制人工批准 |

这个矩阵背后的经验规律是：如果任务可以被明确规格化，就不要先用 LLM；如果任务的主要难点是定位事实，就优先检索；如果任务的主要难点是**把不完整要求转成候选答案**，LLM 才作为主角；如果任务不仅要回答，还要探索、调用工具、写入环境并根据反馈继续行动，才进入 agent 设计空间。Toolformer、RAG、ReAct 和 OpenAI/Anthropic 的工具调用文档共同支持这一点。 citeturn31view3turn30view2turn31view4turn18view1turn19view1

### 重点展开的判断因素

当任务包含多义需求、跨文档整合、跨文件修改、实验方案生成、审稿意见归纳、日志到根因描述这类“**从模糊输入到结构化候选输出**”的转换时，LLM 的边际收益通常最高；而当任务只是阈值判断、权限控制、模式匹配、固定模板填报、精确计算或数据库查找时，传统逻辑、规则或专用系统通常更稳定、更便宜。Toolformer 直接把“算术、事实查找”列为更小专用工具更擅长的领域；RAG 说明知识密集任务要靠外部非参数记忆而不是裸生成。 citeturn31view3turn30view2

“单轮调用”与“多轮 agent”之间最实用的边界，不是 token 长短，而是任务是否满足 agentic 任务的三个性质：持续多步与环境交互、在部分可观测环境中迭代收集信息、基于反馈修正策略。Google 的 agentic 评估和 AgentBench 都表明，真正的 agent 难点不是最终答案文字，而是长期推理、决策和指令遵循；同时，最新的扩展研究也指出，多 agent 并不是默认更好：在并行可分解任务上，多 agent 可能显著提高性能，但在顺序规划任务上反而可能退化，且缺少集中验证时更容易传播错误。 citeturn32view4turn21view3turn27view4

“把 LLM 放在系统中的什么位置”同样关键。作为**默认方案**时，它承担主生成责任，适合高模糊、可验证、收益高的任务；作为**备选方案**时，它只在规则/检索置信度不足时介入，更适合作为路由后的补充；作为**回退方案**时，它常用于对异常输入给出解释性处理或人工工单草稿；作为**裁决器/judge**时，它可用于归并候选、做 rubric 打分或冲突仲裁，但不能无校准地成为唯一裁决，因为 G-Eval 已显示 LLM-as-judge 会对 LLM 生成文本产生偏好，而 agentic benchmark 的最新研究也表明，只看 outcome 容易严重高估系统能力。 citeturn32view1turn27view3turn32view3

### 常见设计方案、权衡与失败模式

最常见的四种调用方案分别是：规则优先、检索优先、LLM 优先、agent 优先。规则优先的优点是稳定、可解释、成本低，但覆盖边界差；检索优先适合“答案在库里”的任务，但对检索质量高度敏感；LLM 优先擅长开放式转换，但需要验证；agent 优先能处理外部反馈和长流程，但引入最大攻击面、状态复杂度和观测成本。CRAG 的结论提醒我们，连 RAG 也依赖检索质量，一旦检索错了，生成会跟着错，因此应把“检索质量评估”单列出来，而不是把 RAG 视为天然安全。 citeturn31view0

典型失败模式包括：把本该规则化的问题交给 LLM 导致不稳定；把需要证据的问题交给裸生成导致幻觉；把需要外部计算/数据库查询的问题交给 LLM 内推理导致事实性错误；把顺序性很强的问题拆成多 agent 导致通信开销和错误积累；把能单轮处理的任务过度 agent 化，结果延迟、成本、攻击面都变大。Google 的扩展研究、AgentBench 与 prompt injection 研究都支持这种“不要无约束 agent 化”的结论。 citeturn27view4turn21view3turn24view4turn20view1

### 可操作的工程模式

在工程实现上，最稳健的是**分级路由模式**：先用规则与专用模块处理确定性高、风险高、成本敏感的请求；再用检索/数据库补足事实；仅对剩余的高模糊、高语义任务调用 LLM；真正需要环境交互时，再进入 agent loop。OpenAI/Anthropic 的工具调用文档都强调，工具调用的本质是让模型发起结构化请求，由应用执行工具并回传结果，这意味着 LLM 应该更多地扮演“策略层”，而不是直接替代工具层。 citeturn18view1turn19view1

一个适合写论文的工程假设是：**越靠近真实世界副作用，越需要把 LLM 降格为建议者，而不是执行者**。因此，读操作可以更自动化，写操作要更强审批；无副作用的信息整合可以单轮，带副作用的环境交互要加验证和人审；对序列计划不要默认多 agent，对高度并行、可分解的子任务才考虑多 agent。这个模式与 NIST 的 trustworthiness 取向、Google 的 agentic scaling 结果和现有工具治理实践是一致的。 citeturn20view0turn27view4turn18view4

### 适合论文中的评价指标

“什么时候调用”这一问题适合用**策略级指标**而不是只看最终 task score。建议至少报告：路由准确率、错误路由代价、在预算内成功率、单位成本成功率、延迟分位数、人工升级率、工具调用次数、回退触发率，以及带副作用任务中的批准前拦截率。对 agent 方案，建议同时报告过程指标与结果指标，因为 ABC 明确建议 agent benchmark 不能只看 outcome，不看过程。 citeturn27view3turn32view3turn19view2

## 应提供什么上下文

### 关键定义

上下文不是“把能找到的东西都贴进去”，而是**把完成当前子任务所必需的控制信号、证据信号和状态信号打包成可管理的上下文单元**。OpenAI 的 prompt engineering 文档把“相关上下文”界定为让模型访问训练数据之外的专有数据、或把回答限制在某些资源上的信息；Anthropic 的 citations 文档则进一步说明，文档块可以被分句或按自定义块切分，从而决定证据引用的最小粒度。换句话说，上下文工程既是“提供信息”，也是“规定模型看见信息的组织方式”。 citeturn18view3turn19view0

### 应提供的上下文类型

在科研与工程项目里，可把上下文分成六类。其一是**控制上下文**：系统约束、角色、目标、输出 schema、禁止项。其二是**任务上下文**：用户输入、业务目标、实验目的、验收标准。其三是**证据上下文**：检索结果、论文片段、手册、API 文档、代码片段、日志、错误栈、测试样例。其四是**状态上下文**：历史对话、先前工具结果、已完成步骤、剩余计划。其五是**执行上下文**：权限、目录、环境变量、依赖版本、运行平台。其六是**审计上下文**：文档 ID、版本号、时间戳、chunk ID、哈希、来源标签。RAG、ReAct、Anthropic citations、OpenAI 工具调用与 prompt engineering 文档都支持这种分层。 citeturn30view2turn31view4turn19view0turn18view1turn18view3

### 上下文选择策略与权衡

“全量给”只适用于输入本身不大、且任务强依赖全局关系的场景，例如较短需求文档到代码骨架、短论文摘要到审稿要点、一个小模块内的 patch 生成。它的优点是简单，不容易漏关键依赖；缺点是 token 成本高，并且长上下文并不等于高利用率。Lost in the Middle 直接显示，模型对长上下文中的中间信息利用并不稳健，相关信息放在开头或结尾往往更容易被利用。 citeturn23view1

“检索给”适用于知识密集但答案不一定在当前输入中的任务，例如文档问答、代码库定位、科研综述辅助。RAG 证明，用显式非参数记忆可以让知识更可更新、可溯源；而 CRAG 进一步指出，检索本身需要质量评估与纠错，否则把低质量证据塞给模型，只会把检索误差放大成生成误差。 citeturn30view2turn31view0

“摘要给/压缩给”适合有长历史、多轮状态或超长代码文档的场景。LongLLMLingua 的结果说明，提示压缩不仅能降 token 成本和延迟，还可能改善长上下文中的关键信息感知；但压缩带来不可逆信息损失，因此更适合先保留原始证据，再按子任务生成摘要而不是只存摘要。 citeturn23view0

“分层给”通常是科研和工程里最稳健的策略：全局层给目标、限制和高层摘要；局部层给当前相关片段；证据层给可引用的原文块；状态层给最近动作与失败原因。这种模式既缓解 lost-in-the-middle，也方便缓存。OpenAI 的 prompt caching 明确建议把静态指令和示例放在前缀，把动态内容放在后部，因为缓存命中依赖精确前缀匹配。 citeturn19view4

“按需给”是 agent 或工具系统的默认思路：先不给全量，把查询、搜索、文件读取、数据库访问作为工具，在需要时拉取。OpenAI 和 Anthropic 的工具文档，以及 MCP 作为 agent-to-tool 标准，都支持把上下文从“prompt 内联”转为“外部可调用资源”。这往往比把整个代码库或整个论文集塞入 prompt 更可控。 citeturn18view1turn19view1turn20view4

### 失败案例与风险来源

上下文失败首先来自**污染与冲突**。NCSC 对 prompt injection 的分析指出，当前 LLM 在提示中并没有天然的数据/指令边界；Anthropic 的 browser use 防御文档也说明，任何被 agent 读取的网页、邮件、文档都可能携带隐藏指令，尤其当 agent 有导航、点击、下载、发送等行动能力时，攻击面会急剧扩大。对科研场景，这一风险已经在 AI-assisted peer review 中具象化：研究显示，少量被操纵的评论就可能改变排序，隐藏 prompt 甚至能把 acceptance score 拉到极高。 citeturn20view1turn19view3turn27view0turn27view1turn27view2

第二类失败来自**过载与过时**。长上下文并不保证有效，尤其在中部信息；而文档、代码、日志又是高变化对象，若没有版本戳和时效控制，模型可能把过时上下文当作真值。OpenAI 的 prompt engineering 文档把 context window 当成可规划资源；在工程系统里，这意味着必须对“放什么进去、放多久、何时淘汰”做显式设计。 citeturn18view3turn23view1

第三类失败来自**隐私与保密**。Springer Nature 与 NeurIPS 的当前政策都要求人类对内容负责，并对评审中的保密信息与 LLM 使用施加限制；Springer Nature 明示编辑和审稿人不应把手稿上传到生成式 AI 工具，NeurIPS 则要求审稿人不得向任何 LLM 泄露投稿内容。科研项目若把全文、评审材料或未公开结果直接送入第三方模型，可能一开始就违反工作流边界。 citeturn28view0turn28view1turn28view2

### 可操作的工程模式

最推荐的上下文工程模式是**版本化上下文包**：每次调用只传一个“可追踪包”，其中包含任务说明、当前输入、检索证据 ID 列表、代码或日志片段 ID、状态摘要、输出契约版本号和权限边界。原始大文档不直接散落在 prompt 里，而是由检索器、文件系统或 MCP 资源管理。这样做的好处是：易于缓存、易于重放、易于回溯失败来源。Anthropic citations 的文档甚至支持把自定义 content block 当作可引用单元，天然适合把 chunk ID 与结果绑定。 citeturn19view0turn19view4turn20view4

另一种重要模式是**未受信上下文隔离**：把用户文本、网页内容、文档原文、日志等未受信数据显式标记为 data/context，而把控制指令固定在不可变前缀；高风险系统再加输入分类器和工具 guardrail。虽然这不能根除 prompt injection，但 NCSC 与 Anthropic 都表明，这种“限制损害半径”的思路比幻想完全消灭 injection 更现实。 citeturn20view1turn19view3turn18view4

### 适合论文中的评价指标

这一问题建议至少报告：检索 Recall@k / MRR、上下文命中率、证据覆盖率、chunk 级引用精度、上下文 token 数、缓存命中率、时效性错误率、冲突检测率、压缩损失率、提示注入攻击成功率，以及“加上下文前后”的性能/成本变化。对长上下文或压缩实验，应单独报告相对性能与延迟，而不是只报最终准确率。 citeturn23view0turn23view1turn19view4turn19view3

## 应输出什么格式

### 关键定义

对于项目代码来说，LLM 输出不是“答案文本”，而是**可被程序消费和治理的输出契约**。OpenAI 把这件事分成两个接口：如果模型要连接系统中的工具、函数或数据，就用 function calling；如果目的是把回复结构化成程序可消费的对象，就用 structured outputs。Anthropic 的工具文档也把“文本答案”与“结构化 tool_use 块”分开，并支持 strict schema conformance。换言之，输出格式设计首先是接口设计，不是提示词修辞。 citeturn18view0turn18view1turn19view1

### 格式选择的实用比较

| 格式 | 最适合的场景 | 优点 | 主要问题 |
|---|---|---|---|
| 自然语言 | 面向人类的解释、草稿、审稿建议、实验构想 | 可读性强，便于协作 | 难自动消费，难约束字段 |
| JSON Schema | 分类、抽取、路由、结构化结论 | 稳定、可解析、可校验 | 表达长证据与引用不自然 |
| XML/Markdown | 需要层次结构且兼顾可读性 | 对复杂提示和中间结构友好 | 仍需解析规范与清洗 |
| 函数调用 | 触发 API、数据库、工具 | 参数受控，副作用边界清晰 | 只能表达动作，不表达长解释 |
| 代码块 | 代码生成、脚本、SQL、配置 | 直接执行或静态分析 | 需要编译/执行验证 |
| patch/diff | 代码修复、重构建议 | 易应用、易审查、可回滚 | 对上下文定位要求高 |
| 测试用例 | 测试生成、回归补充 | 便于纳入 CI | 测试 oracle 质量可能低 |
| 评分表/rubric | 审稿辅助、候选比较、triage | 易审计，便于多评审融合 | 评分理由可能“看起来合理但不忠实” |

这张表的核心含义是：**越靠近自动执行，就越应该使用强约束格式；越靠近人类判断，就越可以保留自然语言层。** OpenAI 的 structured outputs、Anthropic 的 strict tool use 以及 citations 文档共同说明，现代接口已经能把“可执行动作”“结构化对象”“证据支持文本”拆开管理。 citeturn18view0turn19view1turn19view0

### 字段设计原则

无论是科研还是工程，建议把输出字段最少分成六类：`status`（成功、拒绝、需人工、证据不足）、`payload`（核心答案/patch/计划）、`evidence`（文档 ID、chunk ID、页码或引用文本）、`confidence_or_uncertainty`（置信/不确定性说明）、`error`（错误码、失败原因、不可满足约束）、`trace`（模型、版本、schema_version、request_id、context_hash、tool_trace_id）。Structured Outputs 让必填字段、枚举和拒绝更容易被程序检测；Anthropic citations 则说明 evidence 字段完全可以做到块级、页级或字符级定位。 citeturn18view0turn19view0

下面这个极简契约适合科研与工程共享的“结果对象”：

```json
{
  "status": "ok | needs_human | insufficient_evidence | failed_validation",
  "task_type": "code_fix",
  "answer": "简短结论或patch摘要",
  "artifact": {
    "type": "diff",
    "content": "..."
  },
  "evidence": [
    {
      "source_id": "doc-17",
      "chunk_id": "17-4",
      "locator": "p.12"
    }
  ],
  "uncertainty": {
    "level": "low | medium | high",
    "reason": "依赖检索证据不足"
  },
  "error": null,
  "trace": {
    "schema_version": "v3",
    "model": "xxx",
    "context_hash": "xxx"
  }
}
```

### 答案、理由与证据应如何平衡

在需要**人类审查、教学解释、科研可辩护性、文档问责**时，要求“答案 + 短理由 + 证据”通常是最优折中。Anthropic citations 提供块级证据定位；RAG 的经典动机也正是让知识可检查、可更新、可追溯。对审稿辅助、文献综述、实验方案建议、知识问答这类任务，证据字段通常比长篇理由更重要。 citeturn19view0turn30view2

但在需要**自动消费、低延迟、高一致性、避免泄漏敏感推理**时，不应要求模型输出冗长 chain-of-thought。原因有三层。第一，OpenAI 的 reasoning 模型把内部 reasoning token 与面向用户的输出分离，并只在显式请求时提供 reasoning summary；第二，关于解释可靠性的研究已经表明，模型给出的长解释可能只是“看上去很合理”，并不忠实反映真正决策过程；第三，冗长推理会放大 token 成本，增加解析难度，并可能泄露系统提示或中间隐私。更稳健的做法通常是：输出**最终结论 + 可验证短理由 + 可追溯证据 + 不确定性说明**，把真正的验证留给外部系统。 citeturn25view4turn34view0turn34view1

还要注意一个现实 trade-off：某些 provider 的“严格结构化输出”和“内置 citations”并不兼容，说明“既要机器严格解析、又要自然证据插入”在接口层常常需要两阶段设计，例如先输出结构化对象，再用单独一步生成可引用解释；或者先做可引用抽取，再把证据 ID 汇入结构化结果。 citeturn19view0turn18view0

### 可操作的工程模式

在工程中最建议采用**双通道输出**：程序通道只接受严格 schema 或函数调用；人类通道接受解释性文本、来源和可视化。对代码修复，优先要求 `diff + 变更摘要 + 受影响测试`，而不是整文件重写；对实验设计，优先要求 `假设/变量/对照/统计方法/风险提示` 这些槽位；对审稿辅助，优先要求 `评分表 + 证据点 + 未确定项`，而不是模仿“完整审稿长文”。这些都是把 LLM 输出从“文本体裁”改造成“流程接口”。相应地，Anthropic 的 tool_use、OpenAI 的 structured outputs/function calling 以及 citations 都应被视为编排原语，而不是点状技巧。 citeturn19view1turn18view0turn18view1turn19view0

### 适合论文中的评价指标

输出格式问题建议关注：schema 有效率、解析成功率、字段完整率、函数参数合法率、patch 可应用率、测试样例可运行率、引用覆盖率、证据精度、拒绝可识别率、重放成功率，以及人工审计时间。对裁决/评分用途，建议额外报告与人工 rubric 的一致性，以及是否存在对 LLM 产物的系统性偏好。 citeturn18view0turn19view1turn19view0turn32view1

## 如何验证 LLM 输出并接入流水线

### 关键定义

“可用”不应只等于“看起来对”。在科研与工程里，一个 LLM 输出至少要满足几个递进条件：**契约正确**（能被解析）、**内容正确**（事实或逻辑成立）、**执行正确**（代码/查询/计划真的能跑）、**约束正确**（没越权、没违例）、**流程正确**（能接入后续节点）、**可复现**（事后能重放并解释）。NIST 的 GAI 风险框架把 trustworthiness 放在设计、开发、使用和评估全生命周期中考虑；TrustLLM 则把 truthfulness、safety、fairness、robustness、privacy 等维度显式纳入 benchmark。 citeturn20view0turn32view2

### 适合工程实施的验证栈

最稳健的验证不是单个大评委模型，而是**分层门控**。第一层是语法与契约门：JSON schema、类型、必填字段、枚举、patch 语法、SQL AST。第二层是静态门：编译、lint、静态分析、依赖存在性、权限检查。第三层是动态门：单测、集成测试、回归测试、沙盒执行、仿真工具调用。第四层是事实与证据门：引用是否存在、检索证据是否支持结论、是否引用了过时或冲突来源。第五层是一致性门：多次采样一致性、交叉模型/交叉提示一致性。第六层是安全门：输入/output/tool guardrails、提示注入检测、策略规则审查。第七层才是人类审查，通常只留给高风险或高价值节点。OpenAI 的 guardrails 文档、Anthropic 的 eval 设计、NIST RMF 与现有 benchmark 实践都支持这种“多门而非单门”的架构。 citeturn18view4turn19view2turn20view0turn27view3

这套验证栈有一个很重要的现实意义：它把 LLM 从“最终真理源”降级为“候选生成器”。例如代码修复任务里，SWE-bench 本身就是把 GitHub issue 转成补丁任务，再通过测试来判别是否解决；HumanEval 则把“功能正确性”而不是文本相似度作为评测核心。对 agent 任务，Anthropic 的评估文章也明确指出，多轮 eval 需要把任务、环境、工具和 grader 一起设计，而不是只对最终文本打分。 citeturn21view2turn24view2turn19view2

### 自动作流水线中的嵌入方式

一个适合论文和落地实现同时表达的流水线可以写成：

**生成前检查 → LLM 调用/工具调用 → 结构校验 → 静态校验 → 沙盒或测试执行 → 证据核验 → 风险分级 → 通过则提交，不通过则修复/回退/升级人工。**

其中，“生成前检查”可用便宜模型或规则做输入风险筛查；OpenAI 的 block/parallel guardrail 文档明确指出，阻塞式 guardrail 能在高风险输入上提前阻断昂贵模型与工具执行；“工具 guardrail”则尤其适合每次函数调用都可能带来副作用的 agent 工作流。 citeturn18view4

### 验证失败后的重试、修复、降级与回退

验证失败后，最优策略通常不是“盲目多试几次”，而是**带反馈信息的定向修复**。Self-Refine 表明，同一模型在有针对性反馈后可显著优于一次性生成；Self-Consistency 则说明，对复杂推理任务，多样采样后做一致性选择往往优于贪心解码。这启发了一个非常实用的工程模式：把验证器输出（schema 错误、编译报错、失败测试、证据缺口）回灌给模型，只允许它修复被验证器指出的局部问题，而不是整题重做。 citeturn31view1turn31view2

降级与回退应按风险设计。若结构校验失败，可先重试同模型低温重生；若事实/证据失败，可切到检索增强或要求 evidence-only 输出；若执行失败，可要求最小 patch 而非全量重写；若安全门触发，则直接回退到规则系统或人工审批。对于真正高风险动作，NCSC 与 Anthropic 的 prompt injection 研究都提醒我们，不应把“模型自称安全”当成可执行凭据。 citeturn20view1turn19view3

### 适合论文中的评价指标

验证问题建议报告至少四组指标。其一是契约指标：schema 通过率、解析失败率、patch apply rate、tool argument validity。其二是正确性指标：单测通过率、fail-to-pass、集成成功率、事实核验准确率。其三是安全性指标：越权拦截率、提示注入攻击成功率、误杀率。其四是流程指标：平均修复轮数、重试代价、人工接管率、最终提交成功率。对 agent 系统，建议同时报告过程有效性，而不是只报最终结果；ABC 明确表明，一些流行 benchmark 光靠 outcome 会严重高估能力。 citeturn27view3turn32view3turn24view4

## 如何证明调用值得

### 关键定义

“值得”不是只看准确率，而是一个**净价值函数**。建议在论文中显式把它拆成：

**净价值 = 任务收益增量 − 直接推理成本 − 重试与验证成本 − 集成与监控成本 − 风险暴露成本 − 长期维护债务。**

这个分解之所以必要，是因为 provider 文档已经明确把速度、成本、智能视为并列目标；prompt caching 甚至直接把前缀稳定性转化为成本和延迟收益；agent benchmark 研究则显示，多 agent 架构可能在某些任务显著提升结果，也可能显著拉低结果。没有这类分解，“看起来更聪明”的系统不等于“系统层面更值”。 citeturn20view3turn19view4turn27view4

### baseline 设计

一个严谨的价值证明至少需要以下对照组中的若干个，而不是只与“旧 prompt”比较：

| baseline 类型 | 作用 |
|---|---|
| 不用 LLM | 证明是否真的需要模型，而不是普通程序即可 |
| 只检索不用生成 | 判断收益来自检索还是生成 |
| 只规则不用模型 | 判断是否被欠规格任务误导 |
| 小模型替代 | 量化“更大模型”的真实边际收益 |
| 大模型替代 | 判断是否只是模型容量差异 |
| 人类-only | 判断自动化是否真节省人工、还是只把工作后移 |
| 单轮 LLM | 判断 agent loop 是否必要 |
| 单 agent | 判断多 agent 是否只是增加复杂度 |

Anthropic 和 OpenAI 都把 eval-driven design 作为落地方法论；ABC 和 agentic scaling 研究则提醒，模型/架构的收益必须在对照充分时才有解释力。 citeturn19view2turn18view2turn27view3turn27view4

### 收益与成本指标集合

一个可直接放进论文“评价指标”章节的集合如下：

| 指标簇 | 建议指标 | 典型适用任务 |
|---|---|---|
| 任务效用 | 准确率、通过率、解决率、Rubric 分数、引用正确率 | 文档理解、审稿辅助、实验设计 |
| 代码效用 | pass@k、编译率、patch apply rate、fail-to-pass、回归通过率 | 代码生成、修复、测试生成 |
| agent 效用 | 成功率、步数、工具调用数、环境交互次数、任务完成时间 | 代理执行、工作流编排 |
| 人类负担 | 首次可接受答案时间、人工编辑距离、审查用时、工单升级率 | 写作、分析、客服、科研辅助 |
| 系统效率 | p50/p95 延迟、token 消耗、缓存命中率、每成功任务成本 | 所有在线系统 |
| 质量风险 | 幻觉率、证据缺失率、越权率、注入成功率、误拦截率 | RAG、agent、审稿辅助 |
| 长期维护 | prompt/规则复杂度增长、eval 维护成本、回归失败率、模型替换成本 | 所有长期系统 |

这些指标并不是随意拼接出来的：代码侧的 pass@k 与功能正确性来自 HumanEval，issue 解决与测试驱动来自 SWE-bench；agent 侧的环境交互与过程评估来自 AgentBench、Anthropic evals 与 ABC；效率侧则可由 prompt caching 与模型偏好接口显式度量。 citeturn24view2turn21view2turn21view3turn19view2turn32view3turn19view4turn20view3

### 推荐的实验设计与对照组设计

对科研和工程都实用的实验顺序通常是三步。第一步是**离线基准实验**：在固定数据集或回放日志上，比较不同路由、上下文、输出契约、验证器和模型规模。第二步是**受控消融实验**：逐项去掉检索、压缩、工具使用、验证器、人审、缓存、agent coordinator，比较效果与成本变化。第三步是**线上 A/B 或 shadow 模式**：先不直接写环境，只旁路生成建议并记录通过率、采纳率和失败类型，再逐步打开自动提交权限。OpenAI 的 eval-driven 资料与 Anthropic 的 agent eval 方法都强调先建可自动运行的 eval，再上真实用户。 citeturn18view2turn19view2

对“上下文”问题，建议做**上下文消融**：全量给、检索给、摘要给、分层给、按需给，比较准确率、证据覆盖、token 成本与延迟。对“什么时候调用”问题，建议做**路由消融**：规则-only、检索-only、LLM-only、混合路由。对“单轮还是 agent”问题，建议做**拓扑消融**：single-shot、single-agent、centralized multi-agent、decentralized multi-agent，并且固定工具与总预算，避免把计算量差异误当成架构优势。对“输出格式”问题，建议做**契约消融**：自由文本、弱格式、严格 schema、函数调用、双通道输出。Google 的 agentic scaling 研究与 ABC 为这些设计提供了非常直接的实验依据。 citeturn27view4turn27view3turn32view3

### 短期收益与长期维护成本

短期实验里最容易被高估的是“第一次演示成功率”；长期系统里最容易被低估的是：prompt 和规则的耦合债务、检索索引更新、评测集老化、模型升级后的回归、外部协议变更、以及人类对系统过度依赖后带来的审查松弛。NIST 的 GAI 风险框架强调应把风险与评估放在全生命周期中管理；而当前 benchmark 研究也表明，如果任务/评分设计本身不严谨，性能改进可能是幻象。 citeturn20view0turn27view3turn25view0

### 看起来有效与统计上显著有效的区别

在论文中，建议把“看起来有效”和“统计上显著有效”明确区分。前者往往来自 demo、少量案例或主观偏好；后者至少要求：同一测试集上与 baseline 做配对比较；报告均值与方差或置信区间；对人评结果报告标注协议与一致性；对多次采样系统报告随机性范围；对 agent 系统报告过程差异而不是只报单次数值。G-Eval 的结果提示，LLM evaluator 与人工更对齐，但仍然会对 LLM 产物偏好；因此，LLM-as-judge 适合做辅助 grader，不应替代人工 gold set。 citeturn32view1turn19view2turn27view3

## 当前挑战、开放问题与最佳实践

### 当前主要挑战与开放问题

最突出的开放问题不是“模型还不够大”，而是**系统边界尚未稳定**。首先，prompt injection 仍是根本性问题，因为当前模型并没有真正的数据/指令边界，任何读取未受信内容又拥有行动能力的 agent 都存在被劫持的风险。第二，长上下文管理仍不稳，lost-in-the-middle 与摘要压缩的信息损失都意味着“更长”不自动等于“更好”。第三，解释与推理的忠实性仍未解决，长理由会让人类更容易信任，却不保证更接近真实决策过程。第四，agent 评测本身还不够稳定，任务有效性和结果有效性都可能出问题。第五，科研场景还叠加了披露、保密与学术诚信约束，使“能做到”不等于“应该自动化做到”。 citeturn20view1turn19view3turn23view1turn23view0turn34view0turn34view1turn27view3turn28view0turn28view1turn28view2

更细一点看，当前至少有七个值得继续研究的问题。其一，**调用路由学习**：如何自动决定该用规则、检索、专用模型还是 LLM。其二，**上下文预算分配**：在固定 token/延迟预算下如何最优选择 chunk、证据与摘要。其三，**证据化输出接口**：如何同时兼顾严格结构化和高质量引用。其四，**验证器设计**：如何让 verifier 真正衡量目标能力，而不是奖励投机。其五，**agent 架构选择**：何时单 agent 足够，何时多 agent 真有净收益。其六，**科研责任边界**：在审稿、写作和实验设计中，哪些步骤可安全自动化，哪些必须保留强人审。其七，**模型升级后的可复现性**：当 provider 更新模型、定价与上下文行为时，如何保持实验和工程结果可比。 citeturn27view4turn27view3turn19view0turn18view0turn20view0

### 适合落地实施的最佳实践清单

下列清单强调“可操作、可比较、可验证”，适合作为综述的结论性部分，也适合作为工程实施 checklist。

| 最佳实践 | 具体做法 | 为什么有效 |
|---|---|---|
| 先路由再生成 | 先跑规则/专用模型/检索，再决定是否上 LLM | 降低不必要成本，避免把确定性问题交给概率模型 |
| 把 LLM 放在策略层 | 让模型决定“做什么”，工具决定“怎么做” | 工具调用比自由文本更可控、更易审计 |
| 上下文做成版本化包 | 每次调用都记录任务、证据 ID、状态摘要、schema 版本 | 提高重放、追责和回归分析能力 |
| 未受信内容必须隔离 | 把网页、文档、邮件、日志视为不可信输入，限制行动权限 | prompt injection 不会被“好提示词”根除 |
| 优先双通道输出 | 机器通道走严格 schema；人类通道走解释与证据 | 同时满足自动化和审计需求 |
| 高风险只接受最小输出 | 代码修复给 diff，不给整仓库重写；数据库操作给函数参数，不给自然语言命令 | 缩小副作用半径 |
| 验证器要前移 | schema、静态分析、测试、证据核验、guardrails 都放进流水线 | 把错误挡在提交前，而不是上线后 |
| 重试必须带反馈 | 把失败测试、编译错误、证据缺口回灌给模型做局部修复 | 比盲目重采样更便宜、更稳定 |
| eval 先于上线 | 先做离线基准和 shadow 模式，再逐步开自动提交 | 避免 demo 驱动部署 |
| 过程指标和结果指标都要报 | 尤其是 agent 系统，要记录步数、工具调用、失败链路 | 只看 outcome 容易高估系统能力 |
| 科研任务默认保持人类担责 | 评审、方法学、引文与结论都要有明确的人类复核点 | 现行出版政策和近年的风险研究都要求如此 |
| 把“值得”写成公式 | 收益、成本、验证、人力、风险、维护分开核算 | 便于论文比较，也便于工程取舍 |

如果把整份调研压缩成一句最可执行的结论，那就是：**不要把 LLM 当作新的默认计算原语，而应把它当作一个在语义欠规格、知识异构、规则覆盖不足但又可被外部验证的节点上使用的候选生成与策略决策模块；一旦进入真实科研或工程流水线，就必须同时设计上下文工程、输出契约、验证门和价值评估。** 这也是当前软件工程、agent 研究、科研治理与风险管理文献最一致的共识。 citeturn29view3turn22view1turn20view0turn27view3turn27view4
