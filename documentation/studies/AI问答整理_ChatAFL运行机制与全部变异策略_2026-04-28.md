## 3. 核心知识点

### 知识点 1：消息（message）和状态（state）不是一回事

#### 我的疑问链路
消息和状态到底是什么关系 → 为什么会说“发完 `SETUP` 到了 `READY`” → `SETUP` 和 `READY` 明明不是一类东西 → 最终理解点：消息是动作，状态是服务器执行动作后的模式

#### 核心答案
在协议里，`DESCRIBE / SETUP / PLAY / PAUSE / TEARDOWN` 是客户端发出去的请求，也就是动作；`INIT / READY / PLAY / RECORD` 是服务器当前处在的阶段，也就是状态。  
所以“发完 `SETUP` 到了 `READY`”的意思不是“消息变成了状态”，而是“服务器执行完这个请求后，进入了可播放的准备模式”。

#### 通俗解释
把协议想成你在和一台有记忆的机器对话。  
你发的是“命令”，服务器进入的是“模式”。  
命令和模式不是一类东西，但命令会推动模式变化。

#### 形象例子
最适合的类比是“遥控器 / 播放器”：

- `SETUP / PLAY / TEARDOWN` 像你按下去的按钮
- `INIT / READY / PLAY` 像播放器当前所处的模式

比如：

- 按 `SETUP`：播放器完成准备，进入 `READY`
- 按 `PLAY`：播放器开始播，进入 `PLAY`
- 按 `TEARDOWN`：播放器清空会话，回到 `INIT`

#### 为什么是这样
协议服务器不是无状态处理字符串，而是在维护一套会话上下文。  
一个请求是否合理、是否被接受，往往取决于“当前处在什么状态”。  
所以协议 fuzzing 不只是改输入文本，还要理解“这条消息放在当前会话阶段里会发生什么”。

#### 易错点
- 把 `SETUP / PLAY / TEARDOWN` 当成状态名
- 把 `READY / PLAY` 当成客户端发出去的请求
- 看到 `PLAY` 同时是请求名和状态名时混淆两层语义

#### 考试 / 面试回答
在状态化协议中，请求消息和协议状态是两层不同概念：请求是客户端执行的动作，状态是服务器在处理这些动作后进入的模式。像 RTSP 中的 `SETUP`、`PLAY`、`TEARDOWN` 是请求，而 `INIT`、`READY`、`PLAY` 是状态，前者推动后者变化。

### 知识点 2：ChatAFL 从启动到一次 fuzz_one 的完整流程

#### 我的疑问链路
ChatAFL 整体到底怎么跑 → LLM 在什么时候介入 → seed 什么时候被选中和执行 → 新序列什么时候入队 → 最终理解点：它是状态感知序列 fuzzing，LLM 只在少数关键环节参与

#### 核心答案
`ChatAFL` 的运行流程可以概括为：

1. 选择协议并绑定协议适配器  
2. 启动前用 LLM 做 grammar 提取  
3. 启动前用 LLM 做 seed enrichment  
4. dry run 初始 seeds，建立“状态 -> seeds”映射  
5. 主循环中选目标状态、选对应 seed、切 `M1/M2/M3`  
6. 对 `M2` 做多种 mutation，重新拼成完整序列执行  
7. 如果产生新 coverage / 新状态路径 / crash / hang，就保存为新 seed  
8. 长时间没新发现时，再额外调用 LLM 生成一步建议

#### 通俗解释
它像一名会走迷宫的学生：

- 一开始先看规则书：LLM 告诉它“协议长什么样”
- 再补几条初始路线：LLM 给它多一些起步脚本
- 真正探索时，核心还是自己沿着旧路线附近不断试探
- 卡很久才会去问老师：“我下一步大概该怎么走”

#### 形象例子
“迷宫 / 房间 / 钥匙”类比最合适：

- 状态是房间
- 消息是开门动作
- seed 是一段走法脚本
- 新 seed 是被证明“可以带你到新房间”的新跳板

#### 为什么是这样
`ChatAFL` 是建立在 `AFLNet` 上的，所以主干并不是“全靠 LLM 生成输入”，而是“围绕已有 seed 反复局部变异并依赖反馈筛选”。  
LLM 的主要价值在三个位置：

- 启动前补结构知识
- 启动前补起始路线
- plateau 时做单步救场

#### 易错点
- 误以为 `ChatAFL` 每一轮都让 LLM 生成消息
- 误以为初始 seed 决定了最终探索深度
- 误以为只要有 grammar，就自动有深层状态探索能力

#### 考试 / 面试回答
`ChatAFL` 的核心仍是 `AFLNet` 的状态感知序列 fuzzing。LLM 主要在启动前提供 grammar 和 enrichment，在运行期仅在 plateau 时提供单步建议。系统通过 dry run 建立状态到 seed 的映射，在主循环中围绕能到达目标状态的 seed 做局部 mutation，并根据反馈把有价值的新序列加入队列继续探索。

### 知识点 3：M1 / M2 / M3 是什么，为什么要保留 M3

#### 我的疑问链路
`M1/M2/M3` 到底是什么 → 为什么不是整条序列一起改 → `M2` 变了以后为什么还要执行 `M3` → 最终理解点：它是“保留上下文、局部变异、观察后效应”的切分框架

#### 核心答案
`M1/M2/M3` 不是 mutation 方法，而是对一条消息序列 seed 的切分方式：

- `M1`：前缀，用来把服务器带到当前目标状态附近
- `M2`：本轮准备修改的局部块
- `M3`：后缀，用来观察改完 `M2` 之后后续流程会发生什么

保留 `M3` 的原因不是“保证协议完全正确”，而是为了观察 `M2` 改动后的连锁反应。很多新的覆盖、异常状态甚至漏洞，都不是在 `M2` 当场出现，而是在后续消息继续执行时暴露。

#### 通俗解释
它不是“整条路重走”，而是：

- 先照着老路走到门口
- 只改门口那一下怎么开
- 然后继续往后走，看后面会发生什么

#### 形象例子
“实验流程”类比最好理解：

原流程是：

1. 加试剂 A
2. 加热
3. 加试剂 B
4. 冷却
5. 离心

如果你只把第 3 步换掉，真正有价值的不只是“第 3 步有没有立刻爆炸”，还包括：

- 第 4 步颜色会不会异常
- 第 5 步会不会沉淀异常

这里：

- `M1` 是前面准备步骤
- `M2` 是改动点
- `M3` 是后续观察步骤

#### 为什么是这样
协议 bug 往往依赖上下文，不是孤立单条消息触发。  
如果每次改完 `M2` 就停，系统只能知道“这条消息自己是否被接受”，却看不到“它改变内部状态后，后面的流程会走到哪里”。  
保留 `M3` 的本质，是把局部扰动沿着原序列继续传播，看会不会放大成新路径、新状态或 bug。

#### 易错点
- 以为 `M3` 代表一个状态，其实它是后续消息序列
- 以为 `M2` 变了以后 `M3` 就必须完全合法，实际上 fuzzing 正是在观察“不完全匹配”时的异常反应
- 以为 `M1/M2/M3` 本身就是某种 mutation

#### 考试 / 面试回答
`M1/M2/M3` 是 `AFLNet/ChatAFL` 在协议序列 fuzzing 中使用的序列切分框架。`M1` 负责把服务端带到目标状态附近，`M2` 是当前 mutation 的对象，`M3` 是保留的后续序列，用来观察局部改动对后续交互和程序行为的影响。因此它不是 mutation 本身，而是服务于上下文保留和后效应观察的结构化执行方式。

### 知识点 4：所有 mutation 策略有哪些，分别在什么时候用

#### 我的疑问链路
那么多 mutation 到底有哪些 → 是不是每次都全部试一遍 → 什么时候用确定性变异，什么时候进入随机阶段，什么时候才会问 LLM → 最终理解点：mutation 是分阶段组合使用，不是每轮都盲目全开

#### 核心答案
`ChatAFL` 中的 mutation 不是单一策略，而是分阶段上场：

1. **确定性阶段**
   - `bitflip`
   - `arithmetic`
   - `interesting values`
   - `dictionary / extras`
2. **havoc 随机堆叠阶段**
   - `havoc explore`
   - `havoc exploit（grammar-aware）`
   - `region-level mutation`
3. **后备拼接阶段**
   - `splicing`
4. **长期无新发现时**
   - `plateau 时的 LLM 单步建议`

结论不是“每轮都全部试一遍”，而是：

- 新 seed 通常先系统扫一遍确定性变异
- 后续更多进入随机 / grammar-aware 深挖
- 长时间没突破才触发 LLM

#### 通俗解释
可以把 mutation 理解成一支分工明确的队伍：

- 前排先做基础排查：确定性 mutation
- 中排开始大范围试探：havoc
- 再往后尝试拼接和重组：region-level / splicing
- 所有人都试了很久没进展，再去问老师：LLM 单步建议

#### 形象例子
像学生刷题：

- 先按题型系统扫一遍基础方法
- 再开始随机组合技巧猛试
- 还不行就去借别人的解题片段拼接
- 实在卡住，再问老师下一步提示

#### 为什么是这样
不同 mutation 的成本、覆盖面和语义保真度不一样。  
确定性 mutation 成本低、扫面广，适合先发现明显敏感点；havoc 擅长深挖组合空间；grammar-aware 可以减少把消息骨架直接改烂的概率；region-level 和 splicing 可以改变序列结构；LLM 成本最高，所以只在 plateau 时介入。

#### 易错点
- 以为 mutation 每一轮都是随机挑一种
- 以为 LLM mutation 会持续在线参与
- 以为 grammar-aware mutation 等于 LLM mutation

#### 考试 / 面试回答
`ChatAFL` 的 mutation 是阶段化组合策略。新 seed 通常先经历经典 AFL 风格的确定性 mutation，包括 bitflip、arithmetic、interesting values 和 dictionary/extras；随后进入 havoc 阶段进行随机堆叠，其中又可分为普通 explore 和 grammar-aware exploit；必要时再进行 region-level mutation 和 splicing；只有在长时间没有新发现的 plateau 阶段，系统才会基于当前上下文调用 LLM 生成单步建议。

#### 变异策略总表

| 策略名 | 所属阶段 | 改动对象 | 怎么改 | 适合解决什么问题 | 缺点 / 局限 |
|---|---|---|---|---|---|
| `bitflip` | 确定性阶段 | `M2` 中的字节 / 位 | 翻转某些位 | 快速发现最敏感字节 | 很容易把协议打烂 |
| `arithmetic` | 确定性阶段 | 数值字段 | 对数值做加减 | 试边界与偏移 | 只适合数值型位置 |
| `interesting values` | 确定性阶段 | 数值字段 | 塞入典型边界值 | 触发整数边界或解析异常 | 语义较粗糙 |
| `dictionary / extras` | 确定性阶段 | token / 字段片段 | 覆盖或插入关键字 | 引入更像协议的片段 | 依赖 token 质量 |
| `havoc explore` | havoc 阶段 | 整块 `M2` | 多种随机操作堆叠 | 广撒网找意外组合 | 合法性较差 |
| `havoc exploit` | havoc 阶段 | grammar 标记出的可变字段 | 优先改 value 区 | 保持骨架更稳定 | 受 grammar 质量影响 |
| `region-level mutation` | havoc 扩展 | 消息块 / region | 替换、插入、复制块 | 直接改变序列结构 | 可能引入上下文不匹配 |
| `splicing` | 后备阶段 | 两条 seed 的片段 | 把不同 seed 拼起来 | 从别的路线借上下文 | 结果可能很噪声 |
| `plateau 时的 LLM 单步建议` | 长期停滞后 | 当前 `M2` 或下一步消息 | 基于前缀历史给一步消息 | 跨过随机 mutation 难跨的语义门槛 | 只给一步，深度有限 |

### 知识点 5：这些 mutation 到底怎么作用在 M2 上

#### 我的疑问链路
知道名字还不够 → 它们到底怎么改 `M2` → 为什么有些只改值，有些会变长序列 → 最终理解点：`M2` 是变异舞台，不同策略在这个舞台上改的粒度完全不同

#### 核心答案
`M1/M2/M3` 决定的是“改哪一块”，而具体 mutation 决定的是“怎么改这块”。  
所有主要操作都围绕 `M2` 展开，但改动粒度不同：

- `bitflip / arithmetic / interesting values`：偏字节和数值级
- `dictionary / extras`：偏 token 级
- `havoc explore`：整块乱搜
- `havoc exploit`：优先改 grammar 标记出的可变字段
- `region-level mutation`：偏消息块级
- `splicing`：偏跨 seed 重组级
- `LLM 单步建议`：偏语义消息级

#### 通俗解释
你可以把 `M2` 想成一个实验台，不同 mutation 是不同的工具：

- 螺丝刀：轻微拧一拧某个数值
- 小刀：切一小段字节
- 积木替换：整块换掉某个消息
- 借别人的半截模型：splicing
- 问老师下一步怎么装：LLM 单步建议

#### 形象例子
以下都以 RTSP 的 `PLAY` 或其附近为例：

- `bitflip`：把 `PLAY` 中一个字节翻坏，看看解析器是否走到异常分支
- `arithmetic`：把 `CSeq: 4` 改成 `CSeq: 5` 或更大值，看是否引发边界逻辑
- `interesting values`：把 `Range` 改成极端值，试探错误处理路径
- `dictionary`：注入 `Session:`、`Transport:` 之类关键 token
- `havoc explore`：对 `PLAY` 整块做多种随机删改、插入、覆盖
- `havoc exploit`：优先只改 `Session`、`Range`、URI 等 value 区，不轻易打烂 `PLAY RTSP/1.0`
- `region-level mutation`：把别的 seed 中的 `PAUSE` 或 `GET_PARAMETER` 插到 `PLAY` 后面
- `splicing`：把一条 seed 的前半段和另一条 seed 的后半段拼起来
- `LLM 单步建议`：根据 `DESCRIBE -> SETUP` 的历史，直接给出一条更像样的下一步请求

#### 为什么是这样
协议输入不是纯文本，而是“有结构、有上下文的消息序列”。  
因此 mutation 不能只有一种粗暴方法，否则很难同时满足：

- 探索空间足够大
- 协议骨架不至于被立即打烂
- 有能力改变消息长度和序列结构
- 有机会跨过语义门槛

这也是为什么系统同时需要字节级、字段级、块级、跨 seed 级和 LLM 语义级这些不同层次的变异方式。

#### 易错点
- 以为所有 mutation 都只是“改值”
- 以为 region-level mutation 只是普通插入操作
- 以为 LLM 单步建议和 grammar-aware mutation 是一回事

#### 考试 / 面试回答
在 `ChatAFL` 中，`M2` 是 mutation 的主要作用区域，但不同策略的粒度不同。经典确定性 mutation 主要做位级和数值级修改，dictionary/extras 做 token 级注入，havoc explore 做整块随机堆叠，havoc exploit 借助 grammar 约束优先改可变字段，region-level mutation 和 splicing 则能直接重组消息块和序列结构，而 plateau 阶段的 LLM 建议则是语义级的一步消息替换。

#### 为什么这些策略能扩展深度
“原来四条消息，改完还四条，所以永远只能四层”这个理解不完全对，原因有三：

1. **状态深度不等于消息条数**  
   就算还是四条消息，第 3 条的不同 value 或不同方法，也可能让服务器进入新的状态转移。
2. **序列本身是可以变长的**  
   `enrichment`、`region insertion`、`duplication`、`splicing` 都可能让消息序列比原来更长。
3. **新序列会入队，变成下一轮更深探索的跳板**  
   系统不是永远围着原 seed 打转，而是把新发现的完整序列持续变成未来探索的出发点。

### 知识点 6：为什么只是改一个值，也可能产生新路径和新 seed

#### 我的疑问链路
不就是改了一个值吗 → 为什么会说出现了新路径 / 新状态 / 新覆盖 → 为什么这条新序列值得加入 queue → 最终理解点：系统关心的不是“长得新不新”，而是“程序反应有没有变”

#### 核心答案
在协议 fuzzing 中，“新路径 / 新状态 / 新覆盖”不是指消息表面完全变样，而是指程序执行结果真的不同了。  
哪怕只改一个值，也可能导致：

- 走到新的代码分支
- 出现以前没见过的状态序列
- 在后续 `M3` 中暴露新的异常路径

只要这条完整新序列被证明会让程序产生新反应，它就值得被保存成新 seed，成为下一轮的跳板。

#### 通俗解释
系统不是在收藏“看起来花哨的新字符串”，而是在收藏“已经证明有用的新走法”。

#### 形象例子
“山路 / 跳板”类比最好记：

- 原 seed 像一条老路，只能到半山腰
- 你只是换了一个小动作，结果突然拐上另一条岔路，看见了更高的平台
- 那这条“新走法”就值得记下来

另一个更具体的例子是银行表单：

- 表格长得一样
- 只是金额从 `100` 改到 `10000000`
- 走的审批流程、风控流程、日志路径就完全不同了

#### 为什么是这样
服务器处理协议消息时，不是简单比对字符串，而是在按字段值、上下文和会话状态进入不同逻辑。  
所以：

- 一个数值边界
- 一个 `Session` 差异
- 一个 `Range` 特殊值

都可能改变内部执行路径。  
更重要的是，`ChatAFL` 发送的是完整序列 `M1 + M2' + M3`，因此前面的微小变化会在后续步骤里被继续放大。

#### 易错点
- 把“新 seed”理解成“长得特别不一样的消息”
- 以为只有新增消息条数才算新东西
- 把“新覆盖”和“新状态”完全等同起来

#### 考试 / 面试回答
在协议 fuzzing 中，新路径或新 seed 的判定标准不是输入表面差异，而是程序反馈差异。即使只修改一个数值字段，也可能触发新的解析逻辑、错误处理分支、状态转移或后续异常，从而产生新的 coverage 或新的状态序列。一旦某条完整消息序列被证明会带来这种新反应，它就具有继续探索的价值，因此会被加入 seed queue。

---

### 知识点 7：plateau 时 LLM 在做什么，为什么它既有用又有限

#### 我的疑问链路
plateau 是某一条 seed 卡住了吗 → LLM 到底基于什么给建议 → 为什么它有时能突破、有时又不稳定 → 最终理解点：它是基于当前前缀历史的一步提示器，不是持续在线的主引擎

#### 核心答案
plateau 不是“某一条 seed 完全没救了”，而是“最近一段 fuzzing 尝试整体上都没有新发现”。  
这时系统会拿当前正在 fuzz 的 seed 的前缀历史，也就是 `M1` 对应的请求-响应上下文，去问 LLM：

“基于已经走到这里的历史，下一条比较合理的 client request 是什么？”

LLM 返回的是**一步建议**，不是整条新路线。  
它的价值在于：有时能跨过随机 mutation 很难跨过的语义门槛。  
它的局限在于：如果真正的突破需要连续两步甚至三步动作，那么单步建议就可能不够。

#### 通俗解释
它更像一个“卡住时问老师下一步”的功能，不是全程陪练。

#### 形象例子
如果你已经走到迷宫某个拐角：

- 普通 mutation 像你自己不断试不同动作
- plateau 时 LLM 像老师告诉你：“你下一步试试左转”

问题是，如果真正解法是“左转、上楼、再推门”三步组合，那老师只告诉你第一步，还是可能不够。

#### 为什么是这样
LLM 的成本更高，而且当前 `ChatAFL` 的设计本来就是“最小侵入式增强”：  
它并没有取代 `AFLNet` 的主循环，而只是当系统长时间没收获时，补一个更像协议语义的下一步消息。  
因此它的增强点主要是“救场”，而不是“主导深层规划”。

#### 易错点
- 把 plateau 理解为某一条 seed 的局部问题
- 以为 LLM 生成的是整段序列
- 以为只要有 LLM，深层状态就自然能突破

#### 考试 / 面试回答
在 `ChatAFL` 中，plateau 表示近期 fuzzing 尝试整体缺乏新发现，而不是单个 seed 的局部失败。此时系统会基于当前 seed 的前缀请求-响应历史调用 LLM，生成一条下一步消息以替换当前待变异块。该机制的优势是能够跨越部分纯随机 mutation 难以跨越的语义门槛，但由于它只提供单步建议，因此在需要多步协调动作才能进入更深状态时仍然存在明显局限。

## 4. 全局关系总结

这些知识点之间不是孤立的，而是首尾相接的一条链。

首先要理解协议语义：消息是动作，状态是服务器模式。  
在这个基础上，`ChatAFL` 才能把一条 seed 看成“从某些状态走到另一些状态的路线脚本”。  
系统先通过 grammar 和 enrichment 提高初始输入质量，再通过 dry run 建立“状态 -> seed”的映射。  
进入主循环后，它不是整条乱改，而是先根据目标状态选 seed，再切成 `M1/M2/M3`：用 `M1` 走到目标状态附近，只改 `M2`，保留 `M3` 观察后效应。  
真正的 mutation 又不是单一方法，而是按阶段组合：先确定性扫面，再 havoc 深挖，再做 region-level / splicing，最后在 plateau 时才请 LLM 做一步提示。  
每次执行的仍然是完整序列，所以即使只改一个值，也可能改变整段交互的行为。  
一旦出现新 coverage、新状态路径或异常反馈，这条新序列就会变成新的 seed，继续进入下一轮探索。  
因此，`ChatAFL` 的深层探索能力本质上来自“状态感知调度 + 局部变异 + 反馈筛选 + 新 seed 迭代”，而不是单靠某次 LLM 输出。

## 5. 重点结论

- `SETUP / PLAY / TEARDOWN` 是消息，`INIT / READY / PLAY` 是状态，两者不是一类概念。
- `ChatAFL` 的主干是 `AFLNet` 的状态感知序列 fuzzing，LLM 只在 grammar、enrichment 和 plateau 三个位置参与。
- `M1/M2/M3` 是切分框架，不是 mutation 本身；它的作用是保留上下文、局部修改、观察后效应。
- `M3` 的价值不是“保持协议一定正确”，而是把 `M2` 的扰动沿后续流程继续放大出来。
- mutation 是分阶段组合使用，不是单一策略，也不是每轮都无差别全试。
- 新 seed 的价值不在于“长得新”，而在于“程序反应新”；哪怕只改一个值，也可能触发新的代码路径和状态序列。
- plateau 时的 LLM 更像单步救场工具，它能帮助跨过部分语义门槛，但在需要多步协调动作的场景下仍有限。

## 6. 易混淆概念对比

| 概念 A | 概念 B | 区别 | 记忆方式 |
|---|---|---|---|
| 消息 | 状态 | 消息是客户端动作，状态是服务器模式 | 按按钮 vs 设备所处模式 |
| `M1/M2/M3` | mutation 方法 | 前者是切分框架，后者是具体怎么改 | 切哪块 vs 怎么改 |
| 确定性 mutation | havoc | 前者按固定套路系统扫，后者随机堆叠深挖 | 基础排查 vs 疯狂试探 |
| grammar-aware mutation | LLM 单步建议 | 前者仍是程序化变异，后者是基于历史的语义提示 | 自动改字段 vs 问老师一步 |
| 消息条数 | 状态深度 | 条数是表面长度，深度是状态机推进结果 | 几步动作 vs 走到多深 |
| 新覆盖 | 新状态路径 | 一个偏代码层，一个偏协议行为层 | 新代码分支 vs 新状态走法 |
| 初始 seed | interesting seed | 前者是起点，后者是运行中被证明有价值的新跳板 | 起跑线 vs 新平台 |
| plateau | 某一条 seed 卡住 | plateau 是近期整体无新发现，不是单个 seed 局部失败 | 整体停滞 vs 局部卡顿 |

## 7. 复习卡片

Q：为什么目标状态是 `READY` 时，也可能选中 `S0 = DESCRIBE -> SETUP -> PLAY -> TEARDOWN`？  
A：因为 seed 会被挂到它中间可达的状态下，不只是最终状态。`S0` 发完 `SETUP` 后就能到 `READY`，所以可以作为 `READY` 的候选 seed。

Q：`M3` 为什么要保留？  
A：因为很多新覆盖、异常状态甚至 bug，不是在 `M2` 当场出现，而是在改动后的后续消息继续执行时暴露。`M3` 用来观察这种后效应。

Q：`ChatAFL` 的 mutation 是不是每次都全试一遍？  
A：不是。新 seed 通常先经历确定性阶段，后续更多进入 havoc 深挖，长时间无新发现才触发 plateau-LLM。

Q：`bitflip`、`arithmetic`、`interesting values` 的区别是什么？  
A：`bitflip` 是翻位，最粗粒度；`arithmetic` 是对数值加减，适合试边界；`interesting values` 是直接塞典型边界值，适合撞特殊分支。

Q：`grammar-aware mutation` 和 `LLM mutation` 的区别是什么？  
A：前者仍然是程序化 mutation，只是优先改 grammar 标记出的可变字段；后者是 plateau 时基于历史上下文让 LLM 给出一步消息建议。

Q：为什么 `region-level mutation` 能帮助扩展更深状态？  
A：因为它不只是改值，而是能替换、插入、复制消息块，从而让序列变长、结构变化，增加到达新状态路径的机会。

Q：为什么只是改一个值，也可能产生新 seed？  
A：因为系统看的不是字符串表面变化，而是程序反馈是否变化。一个字段边界值就可能让服务器走到新代码分支或新状态路径。

Q：为什么说 `ChatAFL` 的主引擎不是 LLM？  
A：因为绝大多数探索仍然来自 `AFLNet` 的状态感知 seed 选择、局部 mutation 和反馈筛选；LLM 只在三个特定环节增强它。
