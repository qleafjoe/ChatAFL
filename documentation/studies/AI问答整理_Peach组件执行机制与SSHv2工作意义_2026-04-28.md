# [AI问答整理] Peach 组件、执行机制与 SSHv2 工作意义｜2026-04-28

## 1. 本次对话速览

这次对话围绕 `Peach` 的实际工作方式展开，主线不是“怎么写一个 PIT 文件”，而是“Peach 到底在测什么、怎么测、为什么这样测有意义”。

接着进一步追问 Peach 的执行机制：谁负责把测试装起来，谁负责逐轮执行，`StateModel` 是否每轮都重跑，以及这是否意味着永远走同一路径。  
然后讨论了日志的真正用途，结论是日志不是优化对象，而是诊断证据，用来判断应该改 `xml`、改 `py`、改监控，还是提取样本复现。  
在扩展问题里，又补充了两个很关键的现实点：一是为什么 Peach 即使有 `StateModel` 也通常仍算黑盒测试，以及它和 `AFLNet`、`KLEE` 的黑/灰/白盒边界如何区分；二是 SSHv2 Peach 在新 Ubuntu/OpenSSH 上因为 `ssh-rsa` / SHA-1 默认被禁用而失败的根因、修复方向和这项工作的工程意义。  
最后回到更根本的问题：做 Peach 模糊测试的意义是什么。结论是它的最终目标仍然是发现 bug，只不过是用建模、变异、监控把复杂协议的测试过程自动化、可重复化、可定位化。  
结合当前 SSHv2 项目，可以把它定位为：面向 SSH 握手与密钥切换阶段的状态化模糊测试入口，而不是完整覆盖 SSH 全协议的通用测试器。

## 3. 核心知识点

### 知识点 1：Peach 各组件的职责边界
#### 我的疑问链路
各组件分别干什么 → 自己尝试概括 `DataModel / StateModel / Monitor / Mutator / py / Test` → 发现概念边界混淆 → 最终理解点：Peach 不是一个“谁都能做一点”的系统，而是分层明确的装配式执行框架

#### 核心答案
- `DataModel`：定义数据结构，不定义状态流程
- `StateModel`：定义交互流程与动作顺序，不负责底层收发
- `Publisher`：真正负责发送和接收
- `Agent/Monitor`：负责监控目标状态并判定是否异常
- `Mutator`：对可变元素做变异
- `Python`：补充 XML 不适合表达的动态协议逻辑
- `Test`：把这些组件装配成一场可执行测试

#### 通俗解释
可以把 Peach 看成一条装配流水线：

- `DataModel` 规定“零件长什么样”
- `StateModel` 规定“装配顺序是什么”
- `Publisher` 负责“把东西送到目标那里”
- `Monitor` 负责“盯着目标有没有出问题”
- `Python` 负责“那些纯 XML 搞不定的复杂协议细节”
- `Test` 负责“把整条线组起来”

#### 形象例子
最有帮助的记忆方式是：

- `StateModel` 决定“走哪条路”
- `Mutator` 决定“这次路上带什么东西”
- `Publisher` 负责“真的把东西送过去”
- `Monitor` 负责“看对方有没有被送出问题”

#### 为什么是这样
Peach 处理的是复杂输入和复杂交互。如果把“数据结构、状态流程、发送通道、故障判定、动态计算”全混在一起，模型会不可维护。  
所以 Peach 把这些能力拆开：结构由 `DataModel` 管，流程由 `StateModel` 管，执行由 `Publisher` 管，判错由 `Monitor` 管，复杂语义由脚本补齐。

#### 易错点
- 把 `DataModel` 误认为“每个状态的模板”
- 把 `Test` 误认为“负责发送的组件”
- 忽略 `Publisher`，把发送动作错误归到 `StateModel`
- 认为 `Monitor` 只是“看返回值”
- 认为 `Python` 是 Peach 的主流程控制器

#### 考试 / 面试回答
Peach 采用组件化建模。`DataModel` 负责输入结构建模，`StateModel` 负责交互流程建模，`Publisher` 负责真实收发，`Agent/Monitor` 负责异常监控与故障判定，`Mutator` 负责输入变异，`Python` 用于实现动态字段计算、响应解析和加密等复杂逻辑，`Test` 则负责把这些组件装配成可执行测试。

### 知识点 2：Peach 的测试执行机制与 iteration
#### 我的疑问链路
测试是谁封装、谁执行 → 每轮到底怎么跑 → 是否每轮都重新执行同一个 `StateModel` → 如果是，是否永远探索相同路径 → 最终理解点：高层流程通常固定重复，但具体输入变化会让目标内部代码路径变化

#### 核心答案
Peach 的执行链条是：

1. `PIT` 声明组件
2. `Test` 装配组件
3. `Peach Engine` 读取装配结果并启动执行
4. 每轮从 `StateModel.initialState` 开始
5. 按 `Action` 顺序执行 `connect / input / output / changeState`
6. 每步结合 `DataModel`、`Mutator` 和可选 `Python Hook`
7. 通过 `Publisher` 收发
8. 轮次结束后由 `Monitor` 判错并记录结果

#### 通俗解释
Peach 不是“先随机造一个包再试试”，而是“每轮都按固定协议剧本走一遍，只是剧本里的某些台词和参数每次都不一样”。

#### 形象例子
最有帮助的类比是“固定路线，反复换载荷”：

- 路线固定：例如 SSHv2 的 `版本协商 -> KEXINIT -> DH -> NEWKEYS -> 加密请求`
- 载荷变化：cookie、算法列表、长度、字段值、编码、密文内容每轮不同

所以：

- Peach 层面的状态路径可以相同
- 目标程序内部实际走到的解析分支和错误路径可以不同

#### 为什么是这样
协议测试不能每轮都乱改流程，否则大多数样本连握手都过不去。  
Peach 的思路是先把“能到达深处的有效交互流程”固定住，再在这条流程上的输入细节上做系统变异。这样更容易打到深层实现代码。

#### 易错点
- 认为 iteration 就是“重复做完全相同的事”
- 认为固定 `StateModel` 就等于固定代码路径
- 认为 Peach 会自动发现新的高层协议流程

#### 考试 / 面试回答
Peach 的一个 iteration 通常从 `StateModel` 的初始状态重新开始，按既定动作顺序执行完整交互流程。高层协议路径往往保持稳定，但每轮的具体输入会经过变异，因此即使状态转移链相同，目标程序内部仍可能走到不同解析分支、错误处理路径或崩溃点。

### 知识点 3：日志的用途不是“优化日志”，而是指导下一轮优化
#### 我的疑问链路
日志里有什么 → 可以通过日志看到什么 → 下一轮迭代依据什么做 → 是不是就是优化日志文件本身 → 最终理解点：日志是诊断依据，不是优化对象

#### 核心答案
日志主要用来回答四个问题：

1. 失败发生在哪个阶段
2. 这是模型问题、脚本问题、监控误报，还是真实目标问题
3. 问题是否稳定、是否可复现
4. 下一轮该改哪个文件、哪个环节

日志不是最终优化目标。真正会被优化的通常是：

- `sshv2.xml`
- `ssh.py`
- `ssh_authentication.py`
- `Monitor` 判定逻辑
- 超时、连接参数、变异范围

#### 通俗解释
日志的作用像“事故现场记录”。  
你不是为了把事故记录写得更漂亮，而是为了知道事故发生在哪里、谁出的问题、下次该修哪一段。

#### 形象例子
“日志是诊断工具，不是优化对象”是最重要的记忆点。  
看到“认证脚本失败”，下一步不是去改日志格式，而是先判断：

- 服务是不是还活着
- 是加密逻辑坏了
- 还是监控条件太严

#### 为什么是这样
没有日志时，你只能知道“这一轮失败了”；  
有了日志，你才能区分：

- 是 `KEXINIT` 模型错了
- 是 DH / AES / HMAC 计算错了
- 是监控把认证失败误当成崩溃
- 还是目标程序真的被打挂了

#### 易错点
- 以为日志本身就是优化目标
- 把“脚本登录失败”直接当成“发现崩溃”
- 不区分模型 bug、实现 bug 和监控误报
- 不做样本重放，只凭一次日志就下结论

#### 考试 / 面试回答
日志在 Peach 中的核心价值是定位和决策，而不是单纯记录。它帮助分析故障发生阶段、区分测试模型错误与目标真实缺陷、判断问题是否可复现，并据此决定下一轮应修改数据模型、协议脚本、监控逻辑还是提取样本做独立复现。

### 知识点 4：SSHv2 Peach 工作的意义，以及 Peach 模糊测试的最终目标
#### 我的疑问链路
我这个工作有什么意义 → Peach 模糊测试究竟在干什么 → 最终目标是不是发现 bug → 最终理解点：Peach 的意义不在于“写模型”，而在于为复杂协议建立可自动化、可复现、可定位的 bug 发现入口

#### 核心答案
Peach 做的事情可以概括为三步：

1. 对复杂输入和交互流程做建模
2. 在还能到达协议深处的前提下系统制造异常输入
3. 观察目标是否出现崩溃、hang、断连、异常状态或可复现功能错误

所以最终目标仍然是**发现 bug**。  
你的 SSHv2 工作的意义，在于为 SSH 这种带状态、协商、密钥交换、加密和 MAC 的复杂协议，建立了一个真正能跑起来的状态化测试入口。

#### 通俗解释
这项工作不是“写一份配置文件”，而是“把原本很难自动测的 SSH 交互过程，变成一台可以反复自动压测的机器”。

#### 形象例子
最贴切的理解是：

- 没有模型时：像闭着眼往墙上扔石头
- 有了 Peach + 协议脚本时：像沿着正确通道深入建筑内部，再系统敲击各个薄弱点

#### 为什么是这样
SSH 这类协议不是明文单包协议，很多实现只有在：

- 版本协商之后
- KEX 正常建立之后
- NEWKEYS 切换之后
- 甚至进入加密消息阶段之后

才会暴露真正的深层解析与状态处理逻辑。  
如果没有模型和 Python 脚本，测试流量大概率连这些阶段都到不了，更谈不上发现后续 bug。

#### 易错点
- 把“完成建模”当成最终成果
- 把“能跑通一轮”当成已经发现漏洞
- 直接声称“完整 fuzz 了 SSH 全协议”
- 忽略当前模型只覆盖 SSH 的一部分阶段

#### 考试 / 面试回答
Peach 模糊测试的最终目标仍然是发现 bug。其价值在于通过数据结构建模、交互流程建模、变异与监控，把复杂协议实现的测试过程自动化、可重复化和可定位化。对于 SSHv2 项目，这项工作的意义在于为握手和密钥切换阶段建立了可执行的状态化测试入口，使后续发现解析错误、状态处理异常和拒绝服务类问题成为可能。

### 知识点 5：为什么 Peach 通常仍被视为黑盒，而 AFLNet 是灰盒、KLEE 是白盒
#### 我的疑问链路
Peach 明明有 `StateModel` 和状态转移，为什么还是黑盒 → 难道“有状态模型”不就说明它知道程序内部了吗 → 那黑盒、灰盒、白盒到底按什么划分 → 最终理解点：关键不在于有没有模型，而在于是否利用了目标程序内部信息来指导测试

#### 核心答案
`Peach` 通常被归类为**模型驱动的黑盒 fuzzing**，因为它主要依赖：

- 人工定义的 `DataModel`
- 人工定义的 `StateModel`
- 外部可观察结果，例如崩溃、超时、断连、异常响应

它**不知道也不利用**：

- 代码覆盖率
- 分支命中信息
- 基本块路径
- 路径约束

而 `AFLNet` 属于灰盒，是因为它会利用覆盖率和状态反馈来决定下一轮输入；`KLEE` 属于白盒，是因为它直接分析程序内部语义、路径条件和约束。

#### 通俗解释
最简单的判断方法是看：**测试下一步靠什么信息做决策。**

- 黑盒：只看外面
- 灰盒：偷看一点里面
- 白盒：直接研究里面

`Peach` 虽然知道协议格式和交互流程，但这些知识是测试者写进去的，不是从程序内部拿出来的执行反馈。

#### 形象例子
最有帮助的类比是：

- `Peach`：拿着说明书从外面测试机器，知道按钮顺序，但看不到里面电路
- `AFLNet`：除了按按钮，还能看到一些内部指示灯，知道这次比上次多走了哪一段
- `KLEE`：直接打开机器，分析里面电路和条件，推算怎样才能让电流走到某个分支

#### 为什么是这样
“有状态模型”和“有程序内部反馈”是两回事。  
`StateModel` 描述的是测试者建模出来的协议交互状态，例如“先协商、再 KEX、再 NEWKEYS”，它不等于目标程序真实的代码状态或覆盖信息。  
因此，Peach 的“聪明”主要来自外部建模知识，而不是来自内部执行反馈。

#### 易错点
- 以为有 `StateModel` 就一定不是黑盒
- 把“协议状态”误当成“程序内部状态”
- 以为知道输入格式就等于知道程序内部执行

#### 考试 / 面试回答
Peach 通常属于模型驱动黑盒 fuzzing。其 `DataModel` 和 `StateModel` 描述的是测试者提供的输入结构和交互流程，而不是程序内部执行反馈。黑盒、灰盒、白盒的核心区分标准不在于是否存在状态模型，而在于是否利用目标程序内部信息来指导测试；Peach 主要依据外部行为，AFLNet 利用覆盖率和状态反馈，KLEE 则直接分析内部语义和路径约束。

### 知识点 6：为什么 SSHv2 Peach 在新 Ubuntu/OpenSSH 上会因为 `ssh-rsa` / SHA-1 失败，以及这项修复的意义
#### 我的疑问链路
为什么模糊测试在新 Ubuntu 上失败 → 搜索后发现和 RSA 的 SHA 算法被禁用有关，但到底禁用了什么 → 这是 Peach 问题还是 OpenSSH 安全策略变化 → 应该改环境还是改模型 → 最终理解点：失败的根因是现代 OpenSSH 默认禁用了 `ssh-rsa` 对应的 RSA/SHA-1 签名，而现有 SSHv2 Peach 模型把旧算法写死了

#### 核心答案
这个问题的根因不是 Ubuntu 随机失效，而是**现代 OpenSSH 默认禁用了 `ssh-rsa` 的 RSA/SHA-1 签名**。  
你的 SSHv2 Peach 项目仍停留在旧算法假设上：

- `sshv2.xml` 里主机密钥算法只写了 `ssh-rsa`
- `ssh.py` 里协商逻辑要求对端必须支持 `ssh-rsa`
- `ssh.py` 里签名校验逻辑固定按 SHA-1 方式验证

因此在新版系统上会出现两类失败：

- 协商阶段直接失败，没有共同可接受的 host key signature algorithm
- 对端返回 `rsa-sha2-256/512` 时，本地仍按 `ssh-rsa/SHA-1` 解析和校验，导致验证失败

#### 通俗解释
不是 RSA 整体被废掉了，而是“**RSA + SHA-1 这套老签名用法**”默认不再被接受。  
你的 Peach 模型相当于还在用旧钥匙开新门，门不是坏了，是门锁规则升级了。

#### 形象例子
最贴切的理解是“门锁升级”：

- 旧环境：`ssh-rsa` 这把老钥匙还能开门
- 新环境：系统要求 `rsa-sha2-256/512` 这类新钥匙
- 你的模型：还只会拿旧钥匙尝试，自然在入口就失败

#### 为什么是这样
这类失败揭示的是**协议模型与现实实现之间的代差**。  
在复杂协议 fuzzing 里，模型不只是“能不能表达协议字段”，还必须跟得上真实实现使用的现代算法、协商默认值和安全策略。  
否则 fuzzer 甚至到不了深层逻辑，后面的漏洞发现能力就无从谈起。

#### 如何调整
调整可以分三层：

1. **临时环境兼容**
   - 在隔离实验环境里重新启用 `ssh-rsa`
   - 用于快速验证旧模型为什么在旧环境能工作

2. **正确的项目级修复**
   - 在 `sshv2.xml` 中把主机密钥算法扩展为 `rsa-sha2-512,rsa-sha2-256,ssh-rsa`
   - 在 `ssh.py` 中接受 `rsa-sha2-256/512`
   - 重写签名解析和验证逻辑，不再把签名算法和 SHA-1 写死

3. **实验设计层面**
   - 保留旧环境作为历史兼容基线
   - 再用新环境验证升级后的模型
   - 这样能说明问题来源、兼容边界和修复效果

#### 这项工作的意义
这项修复的意义不只是“把实验跑通”，而是：

- 暴露并澄清了现有 SSHv2 Peach 模型的算法边界
- 把一个依赖旧 SSH 默认值的模型迁移到现代系统上
- 让 fuzzing 能真正进入 SSH 更深的握手、KEX 和 NEWKEYS 之后的代码路径

换句话说，这是一项**测试基础设施的现代化修复**，不是简单的环境打补丁。

#### 易错点
- 以为是“RSA 被禁用了”，实际上更准确的是 `ssh-rsa` 的 SHA-1 签名默认被禁用
- 以为监控脚本能登录成功，就等于 Peach 侧的握手逻辑没问题
- 以为只改环境配置就足够，不去修模型和验签逻辑

#### 考试 / 面试回答
新版 Ubuntu/OpenSSH 上 SSHv2 Peach 测试失败的根因，是现代 OpenSSH 默认禁用了 `ssh-rsa` 所使用的 RSA/SHA-1 签名，而现有 Peach 模型在算法协商和验签逻辑中仍将 `ssh-rsa` 与 SHA-1 写死。修复方式既包括隔离环境下的临时兼容配置，也包括更重要的模型升级：支持 `rsa-sha2-256/512`、修改协商逻辑并重写签名解析。其意义在于让 SSH 模糊测试模型从旧安全默认值迁移到现代实现上，从而真正具备继续探索深层协议逻辑的能力。

## 4. 全局关系总结

这几部分知识不是孤立的，而是一条完整链路：

- **组件职责边界**解决“系统是怎么搭起来的”
- **执行机制与 iteration**解决“系统是怎么一轮轮跑起来的”
- **日志与判错**解决“跑完后怎么知道哪里出问题、下一轮怎么改”
- **黑灰白盒边界**解决“Peach 这种带模型的测试方法到底属于哪一类”
- **SSH 兼容性问题**解决“为什么模型正确但现实环境里仍可能跑不通”
- **工作意义与 bug 目标**解决“为什么要做这套系统、最终交付价值是什么”

换句话说：

- 没有职责边界，就无法正确建模
- 没有执行机制理解，就无法判断测试行为是否合理
- 没有日志与判错，就无法迭代优化
- 不理解黑灰白盒边界，就容易把“有协议模型”误判成“看到了程序内部”
- 不处理现实兼容性问题，再好的模型也可能在现代系统上走不到深层逻辑
- 没有 bug 发现目标，前面所有工作都会沦为“只是在写配置和脚本”

## 5. 重点结论

- `DataModel` 管结构，`StateModel` 管流程，`Publisher` 管收发，`Monitor` 管判错，`Python` 管动态协议语义，`Test` 只负责装配。
- Peach 的 iteration 往往重复同一个高层状态流程，但每轮输入不同，因此目标内部代码路径未必相同。
- Peach 默认不擅长自动探索新的高层协议路线，更擅长在一条有效流程上反复换载荷做深度扰动。
- 日志不是优化对象，而是优化依据；真正要改的是模型、脚本、监控或样本复现流程。
- `Peach` 是否算黑盒，关键不在于它有没有 `StateModel`，而在于它是否利用了目标程序内部信息；有人工协议模型仍然可以是黑盒。
- SSHv2 Peach 在新 Ubuntu/OpenSSH 上的失败，本质上是模型还停留在 `ssh-rsa` / SHA-1 的旧安全默认值上，而现实实现已经升级。
- 修复这类兼容性问题的价值，不只是把实验跑通，而是让 fuzzing 模型重新具备进入现代实现深层代码路径的能力。
- 这项 SSHv2 工作的意义不在“写了 PIT”，而在“为复杂 SSH 阶段建立了可自动化、可重复、可定位的 bug 发现入口”。
- Peach 模糊测试的最终目标始终是发现 bug，而不是单纯把模型跑通。

## 6. 易混淆概念对比

| 概念 A | 概念 B | 区别 | 记忆方式 |
|---|---|---|---|
| `DataModel` | `StateModel` | 前者定义输入结构，后者定义交互流程 | 一个管“长什么样”，一个管“先后怎么走” |
| `Test` | `Publisher` | 前者负责装配测试，后者负责真实收发 | 一个是总控绑定，一个是执行通道 |
| `Publisher` | `Monitor` | 前者负责与目标交互，后者负责判断目标是否异常 | 一个在“发/收”，一个在“看/判” |
| 固定 `StateModel` | 固定代码路径 | 高层流程可固定，但目标内部执行分支仍可因输入不同而变化 | 固定路线，不等于固定所有细节 |
| 日志 | 优化对象 | 日志提供诊断证据，真正优化的是模型、脚本、监控和样本策略 | 日志是地图，不是终点 |
| `StateModel` | 内部执行反馈 | 前者是人工定义的协议流程，后者是程序真实运行信息 | 外部脚本 vs 内部轨迹 |
| 黑盒 | 灰盒 | 黑盒看外部行为，灰盒利用部分内部反馈 | 看外面 vs 偷看一点里面 |
| `ssh-rsa` | RSA key | 前者是 RSA/SHA-1 签名算法，后者是密钥类型本身 | 老签名方式 vs 密钥本体 |
| 建模完成 | 发现 bug | 建模是前提，不是最终成果 | 工具搭好不等于问题已找到 |

## 7. 复习卡片

Q：`DataModel` 和 `StateModel` 的核心区别是什么？  
A：`DataModel` 定义数据结构，`StateModel` 定义交互流程和动作顺序。

Q：Peach 里真正负责发送数据的是谁？  
A：`Publisher`，不是 `Test`。

Q：Peach 的一轮 iteration 一般怎么理解？  
A：从 `initialState` 开始按 `StateModel` 跑完整个流程，结束后算一轮。

Q：每轮都重跑同一个 `StateModel`，是不是就没有新探索？  
A：不是。高层状态路径可相同，但每轮输入不同，目标内部代码路径可能不同。

Q：日志的核心用途是什么？  
A：定位故障阶段、区分模型问题与真实目标问题、判断可复现性，并指导下一轮修改。

Q：日志是不是优化对象？  
A：不是。日志是诊断依据，真正优化的是 `xml`、`py`、monitor 或样本复现流程。

Q：为什么 Peach 明明有 `StateModel` 还通常算黑盒？  
A：因为 `StateModel` 是测试者提供的协议流程知识，不是程序内部执行反馈。Peach 主要根据外部行为判断结果，而不是依据覆盖率或路径信息指导下一轮输入。

Q：黑盒、灰盒、白盒最核心的区分标准是什么？  
A：关键看测试是否利用了目标程序内部信息来指导输入生成和路径探索，而不是看有没有状态模型或协议知识。

Q：为什么 SSHv2 Peach 会在新 Ubuntu/OpenSSH 上因为 RSA/SHA 问题失败？  
A：更准确地说，是 `ssh-rsa` 所用的 RSA/SHA-1 签名默认被现代 OpenSSH 禁用了，而现有 Peach 模型把这种旧算法和验签逻辑写死了。

Q：这类 SSH 算法兼容性修复的意义是什么？  
A：意义不只是把实验跑通，而是让模糊测试模型从旧安全默认值迁移到现代实现上，重新具备进入深层协议逻辑的能力。

Q：Peach 模糊测试最终目标是什么？  
A：最终目标仍然是发现 bug。

Q：当前 SSHv2 Peach 工作的合理定位是什么？  
A：它是面向 SSH 握手与密钥切换阶段的状态化模糊测试入口，不是完整 SSH 全协议 fuzzer。
