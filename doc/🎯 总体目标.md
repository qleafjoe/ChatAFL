### 🎯 总体目标

修改 ChatAFL 的 `chat-llm.c` 核心组件，将其原本请求 OpenAI (或其他) 的 API 替换为 **MiniMax `chatcompletion_v2` API**。通过独立的 C 语言单元测试验证 JSON 构建和解析的准确性后，集成到 ChatAFL 中，最后在 `PureFTPD` 镜像中进行端到端可用性验证。

------

### 📋 计划大纲与执行步骤

#### 阶段一：API 接口分析与准备 (静态分析)

**目标**：对齐 ChatAFL 现有的请求逻辑与 MiniMax API 的规范。

- **1.1 解析 MiniMax API 文档**：
  - **Endpoint URL**: `https://api.minimaxi.com/v1/text/chatcompletion_v2`
  - **Headers**:
    - `Authorization: Bearer <API_KEY>`
    - `Content-Type: application/json`
  - **请求 Body (JSON)**: 需包含 `model` (如 `"MiniMax-M2.7"`) 和 `messages` 数组。注意 MiniMax 在 `messages` 中支持传入 `name` 字段。
  - **响应 Body (JSON)**: 目标内容位于 `choices[0].message.content`。
- **1.2 定位 ChatAFL 修改点**：
  - 分析 `chat-llm.c`（或 `aflnet/chat-llm.c`），定位 `curl` 请求的 URL 设置 (`CURLOPT_URL`)、HTTP Headers 组装代码以及 `json-c` 库构建请求 JSON 和解析响应 JSON 的代码段。

#### 阶段二：核心通信代码修改与“脱机”单元测试 (最快验证层)

**目标**：不编译整个 AFL/Docker，单独抽离 `chat-llm.c` 编译测试，确保 API 通信 100% 正确。

- **2.1 代码修改 (Mock & Modify)**：
  - 修改 URL 为 MiniMax 地址。
  - 修改 JSON 组装逻辑，严格匹配 MiniMax 的嵌套格式。
  - 在 `curl` 发送前，**添加 Debug 打印**，将最终生成的 JSON 字符串和 Headers 输出到终端。
  - 在接收到响应后，**添加 Debug 打印**，输出原始 HTTP 响应 JSON 字符串。
- **2.2 独立编译与测试 (脱机测试)**：
  - 编写一个简单的 `main.c`，直接调用 `chat-llm.c` 中的请求函数（传入假造的 fuzzing 状态提示词）。
  - 使用 `gcc main.c chat-llm.c -lcurl -ljson-c -o test_llm` 快速编译。
  - **执行验证**：
    1. 检查控制台输出的原始请求 JSON 是否符合 MiniMax 要求。
    2. 检查发出的 curl 请求是否成功返回 HTTP 200。
    3. 检查控制台输出的解析后自然语言结果是否正确去除了 JSON 外壳。
- **2.3 记录执行结果**：
  - 记录测试的输入 Prompt、截获的 Request JSON、截获的 Response JSON 以及解析后的最终 String。

#### 阶段三：ChatAFL 核心编译与 PureFTPD 宿主机极速测试

**目标**：验证融入 AFL 状态机后，MiniMax API 是否能正确指导 Fuzzing 变异。

- **3.1 核心编译**：
  - 在宿主机（非 Docker 环境）上，进入 ChatAFL 根目录，执行 `make` 编译出原生的 `afl-fuzz` 二进制文件。
- **3.2 极简运行 PureFTPD**：
  - 在宿主机本地编译 `PureFTPD` 源码（打上 afl-gcc 桩）。
  - 启动 Fuzzer：使用刚刚编译的 `afl-fuzz`，指定一小部分初始种子（`benchmark/subjects/FTP/PureFTPD/in-ftp`），对本地的 PureFTPD 开启极短时间的 Fuzzing（例如 5-10 分钟）。
- **3.3 LLM 交互可用性监控**：
  - 观察 AFL 状态面板，查看是否有向 LLM 发起请求的计数。
  - 查看 ChatAFL 生成的日志文件（通常会记录 LLM 产生的 message sequences），确认 MiniMax 模型能够理解 FTP 协议并返回有效的测试用例或状态机序列。

#### 阶段四：Docker 镜像集成与自动化端到端测试

**目标**：确认修改后的代码在标准的 Benchmark 容器化环境中工作正常。

- **4.1 更新项目补丁**：
  - 将确认无误的 `chat-llm.c` 改动生成 Patch（或直接覆盖到挂载目录）。
  - 修改 `benchmark/subjects/FTP/PureFTPD/Dockerfile` 或 `run.sh`，确保构建镜像时使用的是最新的 ChatAFL 代码，并注入 MiniMax 的 API KEY 环境变量。
- **4.2 构建与运行容器**：
  - 执行 Docker build 构建 PureFTPD 测试镜像。
  - 执行 `benchmark/subjects/FTP/PureFTPD/run.sh` 启动完整的 Fuzzing 任务。
- **4.3 最终验证**：
  - 进入容器，检查 `/out` 目录下的 fuzzer 状态和 LLM 日志。
  - 确认 Fuzzing 流程顺畅，未因 API 超时、JSON 解析段错误 (Segfault) 等问题崩溃。
